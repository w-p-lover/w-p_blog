# 持久任务投递恢复与原子认领设计

日期：2026-10-25。Phase6/P6-02/Q1；基线3dfaf44。复用t_ai_task，不建设通用Outbox；先解决任务提交/唤醒/单任务认领，队列阶段整体仍进行中。

## 1. 本批不变量与实施范围

文章与任务同事务持久化；回滚不发唤醒，提交后的投递异常不伪装文章回滚。PENDING行是待办，MQ只是唤醒；发过、confirm ACK不从待办中删除。到期PENDING可以有界重投，多实例通过DB条件更新预约下一投递时间。同一PENDING任务只能有一个执行者，终态/运行中消息不再次执行。失败任务人工重试必须与当前状态和失败次数竞争，RUNNING不可重置。

Q1不自动回收失联RUNNING，不自动重跑RETRYING/FAILED：现有模型/向量副作用和旧正文结果尚无完整版本协议。执行token只约束任务行完成，不等于摘要/向量回写已防旧。不同任务对同文章的旧结果覆盖留Q2，不能把本批称为精确一次处理或完整任务中心闭环。

## 2. 已实现的链路与验证范围

同事务创建/人工重试→afterCommit尽快唤醒；独立短事务预约投递→发送持久mandatory消息→观察confirm/return/未知。定时每轮最多100条到期PENDING，先预约再发；崩溃或结果未知仍依待办到期恢复。预约采用DB时间、30秒到300秒退避，自动恢复仅重发唤醒。单任务PENDING→RUNNING条件UPDATE取得随机执行token，完成按token和RUNNING条件更新；模型调用不包长事务。AI专用监听器AUTO ACK、prefetch1、每实例单消费者，移除其全局内存重试，错误保留数据库状态并按既有DLX拒绝。

验证事务提交/回滚与afterCommit独立预约、发送失败/confirm与return/未知、预约后崩溃恢复、重复投递与双消费者竞争、失败次数/人工重试竞争/拒绝RUNNING，以及实际MyBatis SQL的条件/参数。使用真实事务同步/线程屏障和受控DB/AMQP/处理器，不连接生产或调用付费模型。迁移先核实实际表元数据再执行，本轮只交脚本。

## 3. 数据、事务和状态机

[迁移04](../07-database/04-文章任务投递恢复与认领迁移.sql)只向既有`t_ai_task`增加`dispatch_attempts`、`next_dispatch_at`、`execution_token`和扫描复合索引，没有新建通用消息表。实际数据库元数据未读取、脚本未执行；字段不存在不能运行新版本，迁移SQL不是已部署事实。

- `dispatch_attempts`是唤醒投递预约次数，失败/未知的预约也可能计入，不等于成功发消息次数、模型调用次数或失败次数。INT上限饱和，退避不会因溢出变负。
- `next_dispatch_at`是DB时间裁定的下次可预约时间，NULL立即符合。预约同时条件匹配任务类别、PENDING和到期；先更新下次时间，再递增次数，适配MySQL单表UPDATE赋值从左到右的语义。
- `execution_token`是每次PENDING→RUNNING产生的UUID，成功/失败落状态都要求当前RUNNING且token相同；它不参与摘要SQL和向量写入，不能替代Q2的业务版本/副作用协议。

```text
文章保存事务（已有）
  └─ createArticleTask REQUIRED：写PENDING，与文章一起提交/回滚
       └─ afterCommit尝试唤醒
            └─ REQUIRES_NEW短事务预约next_dispatch_at并提交
                 └─ 事务外发送{taskId}，persistent + mandatory + 独立correlation
                      └─ ack/nack/returned/unknown仅计量，不移除PENDING待办

应用调度每次完成后30秒，首次延后30秒
  └─ SELECT到期PENDING，最多100条，按到期时间/id
       └─ 每条条件预约（竞争失败跳过）→发送相同taskId

AI专用AUTO ACK消费者
  └─ executeTask NOT_SUPPORTED，挂起调用方事务，不用长事务包模型调用
       └─ UPDATE ... WHERE PENDING → RUNNING + execution_token
            ├─ 影响0行：重复/运行中/终态/不存在/其他类型，直接返回
            └─ 影响1行：重新取任务并确认token → 读当前文章 → 原处理器
                 ├─ 正常：WHERE RUNNING AND token匹配 → SUCCESS
                 └─ 异常：相同条件 → RETRYING或达到失败上限FAILED，抛错拒绝重入队
```

RUNNING认领和状态完成使用暂停外层事务后的mapper独立调用，正常MyBatis/Spring配置下每条提交；没有围绕模型网络操作持有数据库事务/行锁。认领成功回复未知、认领后读取任务失败、进程退出或模型结果未知都可能留下RUNNING，本批不会超时重置。若认领失败影响0行，本批不通过读取旧状态来绕过条件；不保证“所有无效taskId都报不存在”的旧内部行为。

重试API是短事务：PENDING只尝试原有到期唤醒，不重置预算或增加新任务；RETRYING/FAILED必须与观察到的失败次数相同且未达max_retry_count才能转PENDING，显式清空旧结果、错误、token和执行时间，并重置投递退避；模型失败次数不清零。RUNNING/SUCCESS/CANCELED和达到上限均拒绝。并发重试只有一个SQL获胜；若任务已进行到另一执行，旧失败次数不能再次重置它。

RETRYING保留既有枚举/接口值，在Q1明确表示未达失败上限的失败记录，须核查副作用后人工重试，不表示后台正在自动调用模型。此前全局listener配置的3次内存重试在AI专用factory中显式移除，不改邮件和搜索factory；同条失败消息不会通过状态回到RETRYING而再次启动处理。未来自动业务重试必须在Q2协议后单独设计，不能悄悄把RETRYING加入扫描条件。

## 4. 投递、确认和消费者边界

每实例每轮查询至多100个ID，下一次扫描发生在上次结束后30秒；每任务预约间隔依次30/60/120/240/300秒，以后300秒封顶。到期PENDING可一直按此速率重发，次数不是有限终止预算；“有界”指单轮条数、逐任务退避和原子预约，不承诺故障后只投递固定次数或30秒内处理完成。多实例可重复扫描候选，但同一到期间隔通常一个预约获胜；预约与消费者认领之间仍允许多条已在途唤醒。

发布器自己构造专用RabbitTemplate、复用现有ConnectionFactory/MessageConverter，mandatory=true，消息明确PERSISTENT；不注册第二个RabbitTemplate Bean，以免导致Boot默认共享template回退、影响邮件。相关confirm依赖现有`publisher-confirm-type: correlated`/returns配置。专用template没有增加自动发送重试；消费ACK、发布confirm和任务状态三者职责不同。

correlation未来完成检查returned优先于ACK，分别记录`ack/nack/returned`；10秒未确认或发送异常为`unknown`。10秒是confirm future的观测超时，不取消已发送消息，不是整个connect/send调用的时间上限；连接故障仍受现有客户端超时制约。ACK也只说明发布确认，不能推断消费者已认领、结果有效或任务成功。扫描从不因ACK而忽略PENDING，因此confirm/return丢失不会丢掉数据库待办。

AI专用factory设AUTO、每实例单消费者、prefetch=1、无内存retry、拒绝不重入队。只有方法正常返回才走容器正常ACK；已成功任务的ACK丢失/重投会被PENDING条件拦住。多实例总消费并发随实例数增长，不是全局1。发生异常按既有AI队列DLX声明转发，但没有把DLX改为quorum或带confirm的故障副本转存，不保证broker每次可靠转存；消费日志改为“需核查持久状态和死信投递”，数据库任务行是主要核查凭据，不能将DLQ声明当作零丢失证据。

## 5. 场景矩阵与恢复

| 触发 | 本批行为 | 剩余边界 |
| --- | --- | --- |
| 正常提交 | 文章与任务提交后才预约并发唤醒；预约独立提交 | 任务成功与文章保存成功分开 |
| 文章/任务事务回滚 | 不运行afterCommit，不预约/发消息 | 假定调用经过Spring事务代理、使用同数据源事务 |
| 前一个缓存afterCommit回调抛错 | 即时唤醒可能被跳过，持久PENDING仍可扫描发现 | 保存接口可能仍报已有缓存同步失败，不伪称所有提交后错误已消除 |
| 提交后进程退出；预约后发消息前退出 | 未预约或到期后仍可扫描，重发原taskId | 不回收RUNNING；恢复依赖DB持久性、调度运行和MQ恢复 |
| 发消息失败、confirm丢失/nack、mandatory return | 不回滚已提交文章，不更改业务成功/失败状态；PENDING到期重发 | 发送未知可能已经到broker/消费者，容忍重复 |
| 收到ACK但消费者停机/积压 | PENDING到期可再次唤醒，处理条件更新去重 | 可产生重复积压，没做全局在途限额或容量实测 |
| 两实例预约/消费者争同任务 | 预约条件与认领条件分别裁决，只有1次PENDING认领启动处理器 | 数据库真实事务/锁仍待联调；不是跨不同任务的文章串行 |
| 模型/向量部分失败 | 任务记录错误/失败次数，消息拒绝重入队；不自动重跑 | 已发生副作用不能回滚；人工重试须先核查，Q2尚未闭环 |
| 运行中人工重试、终态重放 | 不重置RUNNING/终态，不启动第二次处理 | 不提供运行中强制重启入口 |
| 失败任务并发重试/旧重试请求 | 状态+失败次数+上限条件更新，只有获胜者唤醒 | 失败次数达上限不提供自动清零；先定位原因再独立设计恢复 |
| RUNNING崩溃、认领回复未知、完成状态回复未知 | 保留数据库状态和日志，不自动重置 | 需要Q2执行代/副作用恢复；当前可能长期RUNNING |
| 不同任务处理同文章，旧任务晚完成 | Q1未修改原摘要/向量处理器 | 仍可能旧结果覆盖/向量重复，不可标整体幂等完成 |

## 6. 指标与运维核查

新增`blog.ai.task.events{stage,outcome}`固定维度：`scan/error`、`reserve/error`、`publish/sent|error`、`confirm/ack|nack|returned|unknown`。不带taskId、articleId、异常文本；任务ID仅出现在日志。不保证每次scan/reserve成功都有Counter，也没添加实时积压年龄Gauge或告警看板；publish/sent不是最终成功量，unknown不能换算丢失消息数。同次发送异常可能同时记录publish/error和confirm/unknown，不能把两者相加算两次事故。

未来在授权隔离环境按任务ID核查`t_ai_task.status/retry_count/dispatch_attempts/next_dispatch_at/execution_token/error_message/started_at/finished_at`与broker队列/绑定/confirm/日志，先区分PENDING待投递、RUNNING结果未知和失败待核查。禁止用“UPDATE全部RUNNING为PENDING”、直接清队列、批量重放DLQ或清零失败次数作为常规恢复。PENDING连续扫描失败看DB/字段/索引与调度日志，returned看交换机/绑定/路由，unknown看网络/确认配置并保留重复处理可能；原taskId不变。

## 8. Q2：正文身份、派生发布与部分完成恢复

2026-10-26，在Q1基础上集中补齐。第1—7节为Q1实施记录；本节更新当前源版本与副作用协议，不改变Q1投递/ACK/失败预算及不回收RUNNING的边界。

### 8.1 业务触发与身份选择

作者连续保存A、B两版，处理A的任务晚完成；或者摘要已生成但第二批向量写入失败。原实现任务没有受理时正文身份、摘要按articleId无条件覆盖、分块随机ID不断追加，仍公开的文章可在问答中命中旧正文。`content_version`会随AI摘要改变，用它同时表示作者正文和派生发布会让当前向量因摘要更新自行过期。

采用三个明确职责：

| 字段/身份 | 改变时点 | 业务含义 |
| --- | --- | --- |
| Article.source_version | 作者通过现有保存入口创建/编辑，每次UUID | 此次作者保存的标题/正文身份；即使文本改回旧值也取得新身份，阻止ABA旧结果复活 |
| Article.content_version | 作者保存与AI摘要成功发布 | 详情缓存选择版本，保留C3a权威校验；不用于任务源版本判断 |
| Article.indexed_source_version | 当前源版本的全部向量批次返回成功后条件写入 | 当前源向量的发布凭据；作者编辑同事务清空，不是跨MySQL/Qdrant原子事务 |
| AiTask.source_version | 创建任务时读同事务持久文章并核对标题/正文 | 受理时源身份；不保存第二份完整正文，不将旧任务偷偷升级到当前版本 |
| AiTask.generated_payload | 摘要与标签均非空后，RUNNING/token条件写入 | 已生成检查点，含sourceVersion/summary/tags；失败与人工重试保留 |

每次作者保存均产生新源身份，包括仅改其他文章字段的保存。独立分类/标签改名不改正文身份，读取仍按当前权限过滤。编辑事务在更新source/content版本后清空旧摘要、标签、索引时间和发布凭据；回滚一起撤销。数据库外绕过该保存协议直接改正文而不改source_version不在保证内。

没有沿用缓存版本，没有以内容hash替代作者保存代际，没有引入通用事件平台、额外向量库或文章历史全文表。源身份已足够阻止不同作者保存之间的覆盖；不宣称提供作者编辑冲突检测。

### 8.2 正常与乱序时序

```text
作者保存事务：写source_version/content_version → 清旧AI展示和向量发布凭据
  → 同事务建绑定source_version的PENDING任务 → Q1提交后唤醒/持久扫描
消费者原子认领：RUNNING/token → 读文章
  ├─ 源缺失/版本已换/文章不存在/非PUBLIC/已删除：CANCELED，不调用模型、不消耗失败次数
  └─ 当前源：读检查点，或生成摘要/标签后按RUNNING/token持久化检查点
       → 原始正文分块 → 分批写向量，每批最多10片
       → 最终UPDATE同时校验文章源版本、PUBLIC/未删及当前任务RUNNING/token/归属
            ├─ 1行：摘要/标签、索引时间、缓存新版本、向量发布源版本同一条SQL发布
            │     → Q1按token写SUCCESS，outcome=PUBLISHED
            └─ 0行：业务已过期/撤回，按token写CANCELED，outcome=SUPERSEDED_OR_WITHDRAWN
```

旧任务A运行期间作者保存B，A已经发生的模型请求不能撤销，也可能继续写A的向量；最终摘要UPDATE因源身份不符影响0行，不能覆盖B。B可独立处理并发布；A/B向量身份隔离，A晚写也不覆盖B的点。撤回/删除时同样不允许最终派生发布。先撤回再原样恢复且源身份未变时，已有完整向量可再次通过当前可见性检查；通过作者保存恢复会换源，旧向量继续拒绝。

单任务token与source_version职责不同：token保护任务认领/检查点/最终发布条件，source保护不同任务及历史回填的文章身份。不同任务处理同一个source时，原始标题/正文一致，分块点一致；摘要生成值仍可能不同，同源最后一次有效发布可覆盖前一次同源摘要，未实现跨任务只生成一次模型请求。

### 8.3 向量身份、失败与恢复

点ID为`UUID.nameUUIDFromBytes(UTF8("article-chunks-v1:" + articleId + ":" + sourceVersion + ":" + chunkIndex))`，metadata增加sourceVersion，保留articleId/title/规范URL/chunkIndex/chunkTotal。分块算法仍1200字、重叠150字。已读取当前依赖Spring AI Qdrant Store 1.0.0公开sources.jar：doAdd使用`UUID.fromString(document.getId())`构造点并调用`qdrantClient.upsertAsync(collectionName, points).get()`。这是提供者代码依据，未连接真实Qdrant验证一致性、持久性或网络未知行为。

| 触发 | 恢复与结果 | 明确边界 |
| --- | --- | --- |
| 第二批向量失败 | 不写发布凭据；任务按Q1失败落状态。人工重试读取已持久摘要/标签，所有分块复用稳定点ID再upsert | 已成功批次不回滚；可能重新Embedding产生费用，不是费用精确一次 |
| 检查点写入失败/回复未知 | 抛错，不开始向量/发布；下一次重试以实际数据库检查点为准 | 模型已返回但检查点未落库仍可能再次生成；没有供应商调用幂等协议 |
| 向量全部成功、最终发布异常/回复未知 | 不伪称成功，任务可能失败或RUNNING；若失败状态可人工重试，继续复用检查点/点ID | RUNNING尚无自动回收；不能因下游幂等就盲目并发重跑模型 |
| 发布成功、任务完成状态异常/ACK丢失 | 任务状态按Q1保持独立；重复消息不能再次认领RUNNING/终态 | 发布凭据不等于任务状态已完成；崩溃后仍可能需核查RUNNING |
| 作者编辑/撤回与最后发布竞争 | 在实际数据库条件UPDATE的观察点决定是否发布；读端另查当前源/权限 | 真实MySQL行锁/隔离与跨进程竞争未验收；SQLite不是其替代证据 |
| 历史回填 | 每篇按同一源构造相同点；所有批次完成后按源/PUBLIC/未删发布，仅计成功发布的分块数 | 不改摘要；接口返回仍是分块数量。原入口从最小ID取有限篇，无持久游标，不是全库接续工具 |

版本发布保护完整性选择，不保证向量必然可用。向量写后丢失、集合被清空或未来模型/分块schema变更，需要单独核查/回填。旧版与部分未发布点暂不物理清理，topK=5可能被旧点占满而减少召回；允许明确无可用来源，不放宽版本校验换召回。清理/过滤前推待容量证据，不新建索引平台。

### 8.4 问答读取边界

现有两次可见性批量查询升级为`selectVisibleAiArticles`：同一SQL保留PUBLIC/未删/私人分类与标签规则，且要求indexed_source_version=source_version，返回id/sourceVersion。每片metadata源身份必须与该数据库当前源相等。无版本历史点、旧版本点和未发布当前批次不进入模型上下文。生成后再次查询实际使用来源；任一源或权限变化，拒绝整个答案与引用，错误为“参考文章的内容或访问范围已变化，请重新提问”，不自动再生成。保留精确articleId解析和规范引用URL。

此保证仍以两次数据库查询可见快照为界：首次查询后编辑时，旧上下文可能已发送给供应商；第二次只能阻止向读者返回，不能退回费用或追回外部请求。第二次之后的变化、主从延迟、已显示答案无法追回。仍信任内部向量生产者正确绑定正文与articleId/sourceVersion，未对数据库/向量恶意篡改作密码学证明。

## 10. Q3执行租约、检查点接续与发布事务（2026-10-27）

本节取代第8节关于“RUNNING不自动恢复、发布与任务完成独立”的当前行为描述；第8节保留为Q2交付历史。原作者源身份、稳定向量点和问答两次权威校验继续有效。本批不新增表、列、配置开关或通用任务平台，不执行数据库脚本、不启停/部署服务。

### 10.1 触发、缺口与承诺

业务触发：作者保存公开文章后，消费者可能在模型调用、向量第二批、最终数据库提交或ACK途中失联。作者需要区分“可自动接续”与“供应商结果未知”，不能因恢复造成无预算的模型重跑，也不能由已失去执行资格的旧工作线程覆盖新执行结果。

Q2的检查点能减少人工重试时的摘要生成，但RUNNING可永久悬挂；最终文章UPDATE与任务SUCCESS是两次提交，单独的EXISTS token条件不足以证明加入租约回收后的竞争安全。Q3将最终发布与终态合并成一个任务行锁保护的短事务，并把可自动恢复范围限制在持久检查点之后。

本地协议承诺：同一任务的最终文章派生发布和SUCCESS/CANCELED一起提交或回滚；回收作废旧token后，旧执行不能保存检查点、续租、发布或完成任务。没有检查点的失联/执行异常进入UNKNOWN，普通重试和扫描都不能使其重新调用模型。此处是实现与受控证据范围；真实MySQL锁/隔离、真实依赖故障及统一切换仍待验收。

### 10.2 状态与时间字段

复用`next_dispatch_at datetime(6)`及既有`(biz_type,task_type,status,next_dispatch_at,id)`索引，时间判定使用数据库NOW(6)。其语义由status决定：

| 状态 | next_dispatch_at语义 | 自动处理 |
| --- | --- | --- |
| PENDING | 下次投递预约时点；NULL立即可预约 | Q1扫描/退避发送同一taskId，confirm不移除待办 |
| RUNNING | 本次执行租约到期时点 | 认领、成功保存检查点、每个向量批次前续租为数据库当前时间+900秒；已到期不可复活 |
| RETRYING | 有检查点的业务退避时点 | 到期且未耗尽失败预算才条件转PENDING，保留检查点与累计失败次数 |
| UNKNOWN | 模型/执行结果须人工核查 | 不自动执行，不允许普通retryTask重置 |
| FAILED | 失败预算已耗尽 | 不自动执行，不清零预算 |
| SUCCESS/CANCELED | 已完成/当前源已失效 | 不再次认领；旧消息无业务副作用 |

默认最大累计失败次数仍为3，正常异常和失联回收共用预算。失败后按`min(300,30*2^min(累计失败次数,4))`秒退避，默认前两次分别60/120秒，第三次FAILED；人工可提前重试有检查点且未耗尽的失败行，但不能重置失败次数。扫描每次最多100条恢复候选和100条PENDING，完成后30秒再次调度；这些是批量/间隔边界，不是全局吞吐、最大恢复耗时或broker积压上限。

15分钟是无进度的执行租约，不是模型/Embedding网络请求总超时。每批最多10片，批次之间续租；不新增独立心跳线程。单批外部调用超过租约时，旧请求可能仍运行；恢复后可能重复Embedding并计费，但同源/同分块点身份不变。摘要/标签供应商未提供调用幂等协议，不能写费用一次或外部副作用精确一次。

### 10.3 执行、发布与竞争时序

```text
PENDING条件认领 → RUNNING/新token/15分钟租约 → 校验文章当前源与公开状态
  ├─ 源过期/无源/已撤回：最终短事务内CANCELED，不调用模型、不消耗失败预算
  └─ 当前源：只有generated_payload为NULL才首次生成摘要/标签
       → 检查点按RUNNING/token/未过期租约写入并续租
       → 每批向量前条件续租 → 稳定点upsert（全部网络调用在事务外）
       → AiTaskExecutionService.finish的独立短事务：
            SELECT任务 ... FOR UPDATE → 校验token并条件续租
            → 文章按源/公开/未删/任务归属条件发布
            → 同一事务写SUCCESS或CANCELED并清token → COMMIT → 允许消费者正常返回/ACK
```

`finish`与`fail`经独立Spring Bean代理执行REQUIRES_NEW，声明10秒事务超时；这不是所有驱动/锁等待/网络总时长的硬上限。锁顺序为先任务行，再文章条件UPDATE；模型与向量不在持锁事务内。作者保存更新文章源仍会通过文章条件阻止旧源发布。已有历史回填入口不参与任务终态，但同样受源/可见性条件约束。

| 触发/竞争 | 协议结果 |
| --- | --- |
| 回收UPDATE先取得任务行并到期成功 | 状态退出RUNNING并清旧token；旧finish锁查询无行，不发布/完成；新认领使用新token |
| finish先锁到有效任务行 | 条件续租后在同一事务更新文章/终态；回收等待该行锁，提交后其RUNNING条件不再成立；回滚则无文章发布，任务仍可按持久状态恢复 |
| finish锁到已过期、尚未被扫描的任务 | 条件续租0行，不发布；保留RUNNING供到期扫描处理 |
| 文章发布执行后，任务终态写入失败 | 整个短事务回滚；不留下本次摘要发布但任务仍RUNNING的分裂提交 |
| 提交成功但客户端/ACK结果未知 | 任务与文章已一起提交；失败处理重新锁查不到RUNNING，不能把SUCCESS改成失败；旧消息不能再次执行 |
| 失败处理与回收/新执行竞争 | fail重新锁读持久任务与token；旧token无行时不改预算或状态；同一有效执行最多由一方完成状态转换 |
| 旧向量网络调用在回收后才返回 | 不能取消已发出的外部请求；同源同schema稳定点可覆盖同一身份，不能发布旧执行结果；换源点隔离，读端拒绝旧源 |

这些锁顺序与条件是设计依据，不把SQLite数据库级写锁等同于InnoDB行锁；真实MySQL并发/隔离、锁等待及死锁重试仍未实测。不同任务处理同一作者source仍允许最后一次有效同源摘要覆盖，不承诺跨任务模型去重。

### 10.4 失败、UNKNOWN与接续

1. 普通异常时，在独立短事务重新锁读数据库检查点，避免检查点提交成功但响应丢失后按旧Java对象误判。持久检查点存在才RETRYING/FAILED；不存在则UNKNOWN。首次文章读取等前置失败也保守归为UNKNOWN，需核查是否实际发过供应商请求。
2. 超时扫描用条件UPDATE与最终发布竞争同一任务行：有检查点→计一次失败、RETRYING或FAILED；无检查点→计一次失败、UNKNOWN。清token后等待下一业务退避，不立即开始新执行。
3. RETRYING到期条件转PENDING，随后走既有持久投递。DB故障/恢复响应未知时以持久行决定；不依赖DLQ副本完整，不回放旧DLQ。未知/失败状态留在现有任务列表和错误信息中。
4. 检查点只在SQL NULL时允许首次生成。空串、纯空白、非法JSON、错误source或缺摘要/标签均报错，不能降级成重新调用模型；坏检查点最多按预算失败，空白被失败处理隔离为UNKNOWN。稳定点重复并不意味着供应商费用不会增加。
5. UNKNOWN需结合任务创建/开始时间、业务源、供应商用量/请求日志和实际持久检查点核查；本批没有供应商幂等或核账API，也没有“确认重跑并重新授权费用”的专用接口。不能用普通重试按钮、直接SQL清预算或批量改PENDING替代核查。是否重新发起文章处理必须显式接受可能重复费用，自动化不做该操作。

### 10.5 必要观测与运行门槛

复用BlogMetrics的有限stage/outcome事件，增加recover expired/resumed、finish fenced/published/canceled、failure fenced/retrying/failed/unknown；已发布/失败状态事件在提交后记录，仅作诊断，不是持久业务账本。增加按五个固定状态的`blog.ai.task.backlog`和`blog.ai.task.oldest.seconds`，数量来自数据库，年龄从最早create_time算起，覆盖UNKNOWN/FAILED而不是只统计可执行队列。`blog.ai.task.snapshot.timestamp`是最近成功快照的Unix秒，0表示未成功；扫描失败时旧值可能过期，应结合snapshot时间与scan/error事件排查，不能把0条初值当健康。

运行前必须统一停旧消费者/写入协议并核查任务状态。Q1/Q2的next_dispatch_at原为投递预约，不是租约；不能将旧RUNNING或旧RETRYING的该字段直接解释成新租约/业务到期并启动自动恢复。没有期限的旧RUNNING不会被本批自动回收。2026-10-26迁移时0任务只是当时快照，本轮未再次连接业务库，不能据此认定部署时仍无在途任务。无需新DDL，但不支持旧新协议混跑；分块schema、向量模型/维度配置也须统一。

“忽略成功回复”是受控的结果未知/重复演练，不是网络丢包。Java链路的文章处理器被显式替换，其他任务/事务/投递/监听代码采用生产类；没有启动整个应用扫描历史任务。搜索的故障副本和重放属于独立链路，AI任务待办不能替代Canal/ES恢复证据。

## 12. 搜索故障批次的可执行恢复边界（2026-10-29）

AI任务以数据库PENDING为待办；Canal搜索同步以MQ故障副本为恢复凭据，两者不能互相替代。现有ArticleSearchSyncConfig/ArticleConsumer已提供每次投递3次重试、confirm且无return才允许完成故障转存、按文章ID读取当前数据库的整批处理。缺口是运维05只有人工协议，无法直接执行“修复依赖后重新进入消费链”。

本批采用一次性Python AMQP客户端，复用原交换机/队列和body，不新增业务表、通用重放平台、常驻消费者或管理API。默认仅被动计数；明确主机/vhost与execute后，至多1—100条手动ACK获取，先整批校验并落盘审计，再持久mandatory发布并等待confirm，确认无return后才发送源ACK。没有“先自动确认导出再发”的数据丢失窗口。主键/表/操作错误保留源并停止，不自动修补或跳过。

正常路径、发布失败、确认未知、确认后/源ACK前中断、坏消息和重复处理共用原消费语义。publish_confirmed≠索引完成；源ACK没有确认应答，未知可能重复；旧TTL/user_id不复制，body/错误上下文保持。审计逐阶段fsync，主机/vhost/哈希/文章ID用于关联而非去重，不能承诺broker崩溃无损。命令子进程120秒受父进程监督，避免把socket_timeout误写成confirm期限。

方案取舍：不增加未装配认证/权限的管理HTTP端点；不建立可自动重跑所有坏消息的定时回灌；不直接写ES，仍走当前数据库事实同步；不盲跑业务故障队列；不改已有共享RabbitTemplate和其他队列。逐条确认成本/遇坏队头停止是首版保守恢复的边界，批量并发、格式修复/选择性跳过等有真实需求再设计。
