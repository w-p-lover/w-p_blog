## 1. 业务范围与阶段决定

## 2. 数据与状态规则

| 对象 | 职责 |
| --- | --- |
| t_activity | DRAFT/PUBLISHED、报名开始/结束、总量capacity/余量remaining、持久待办数pending_count |
| t_activity_registration | UUID请求主键、活动/用户唯一身份、业务结果、投递代/退避、处理失败次数/简要原因 |

活动开始/结束指报名窗口：`starts_at <= DB NOW < ends_at`。服务端采用数据库时间判断，不能由前端倒计时裁决。已发布但尚未开始可以改时间/容量；开始后全部配置不可修改，无删除/关闭API。新建/修改还要求新的开始时间在未来。活动初始remaining=capacity；首次发布必须在开始前。

请求状态：PENDING（已持久受理）→CONFIRMED（已确认占有名额）/SOLD_OUT（本次售罄终态）/CANCELED/FAILED（3次记录到的确认事务失败）。CONFIRMED→CANCELED只释放一次；PENDING→CANCELED只减少待办，不增加名额；FAILED释放待办预算、未占有名额，有权限的管理员可恢复为PENDING。SOLD_OUT/CANCELED不能恢复或重新报名，不自动候补。对原已受理FAILED的人工恢复允许在窗口结束后执行，与原PENDING窗口结束后继续确认一致。

`request_id`全局唯一，(activity_id,user_id)唯一；userId只来自StpUtil认证，报名DTO不接受userId。UUID规范化为小写。相同请求号/相同用户活动返回当前身份；同用户换新请求号仍返回原身份；跨用户或跨活动复用已占请求号拒绝。唯一冲突后用SELECT FOR UPDATE当前读查事实，不靠REPEATABLE-READ旧快照。取消后唯一身份保留，不能换请求号绕过。

MySQL5.7不依赖CHECK约束：库存边界由应用封装的条件UPDATE和短事务保证，无通用改库存接口。迁移无业务外键：没有活动删除API，历史报名保留，应用在同一事务中校验/竞争活动；不要绕过服务直接改表。

## 3. 受理、确认与取消事务

```text
登录/活动级Redis限流
  → INSERT唯一PENDING身份
  → 活动行条件UPDATE：已发布、窗口内、pending_count < 1000，待办+1
  → 同事务提交后仅向有界后台线程提交唤醒 → 返回PENDING

Rabbit唤醒(requestId,dispatchToken)
  → 短事务：SELECT匹配PENDING/token的请求行 FOR UPDATE
  → 条件扣余量并减待办 + 写CONFIRMED，同事务提交
  → 余量0：减待办 + 写SOLD_OUT，同事务提交
  → 提交后AUTO允许ACK

取消：锁当前用户请求 → PENDING减待办 / CONFIRMED条件回库存 → CANCELED，同事务
```

受理插入身份在前、活动行在后；确认/取消/失败记录/人工恢复均为请求行→活动行，避免协议自身反转加锁顺序。活动配置只更新活动行，不反向锁请求。受理预算不满足抛业务异常使插入回滚，不遗留已受理请求。条件写入影响行数都检查；终态写入失败回滚容量/待办变更。

同请求并发处理以请求行串行，终态/旧token不扣减。不同用户争最后名额由同一活动条件UPDATE `remaining > 0`竞争；remaining不能变负。确认已提交ACK未知再投时看到终态直接返回。确认和取消竞争：取消先赢则不确认；确认先赢则取消释放其占用，重复取消不释放第二次。已受理请求结束后仍有资格处理；没有FIFO/绝对先到先得保证。

## 4. 持久投递、故障与恢复

PENDING是业务待办，MQ只是唤醒。独立活动交换机/队列，不复用AI任务或搜索故障队列；不替换共享RabbitTemplate。afterCommit只入本地有界executor（1线程/100等待/AbortPolicy），满或停机仅记录deferred，HTTP线程不执行MQ网络发送。没有长时间数据库事务跨网络调用。

扫描完成后5秒再执行、每轮最多查100个到期PENDING；在独立REQUIRES_NEW短事务中条件预约，同一处理轮次保留dispatch_token（仅为空才创建），30/60/120/240/300秒封顶退避，锁内读回持久代后发送mandatory消息。失败记录清代后才产生下一处理代，详见第9节。多实例可能重复唤醒；只有当前投递代能处理/记录失败。confirm ACK不移除PENDING、return/NACK/未知不回库存，提交后进程退出仍由到期待办发现。10秒future仅为确认观测期限，不是send总耗时；若底层发送长时间阻塞，单发送线程会停滞，余下持久待办可查、活动预算会拒绝新增，需恢复连接/实例而不是宣称自动取消网络调用。执行器预算是单实例，活动待办预算在数据库上跨实例生效。

消费者独立AUTO/1并发每实例/prefetch1/无继承内存retry。业务处理只有DB短事务，不需要模型任务那种长租约；消息提交异常后独立事务先锁当前请求检查PENDING/token，结果已CONFIRMED不再记失败，旧代错误不伤新执行。可记录的失败次数到3进入FAILED、释放待办预算，其余退避扫描恢复。记录失败也遇数据库故障时拒绝本次消息；原PENDING仍保留。DLX仅是诊断副本，classic队列DLX不承诺无损，不能代替持久请求恢复。损坏/缺身份消息拒绝不自动回灌。

存储故障使失败记录也提交不了时，失败次数不增长，无法承诺全生命周期最多3次投递；MQ长期不可用/无人消费时PENDING也不自动变售罄或失败。每次scan返回上限不是全库扫描成本保证。需按业务真实积压补排空/索引/尾延迟证据，不预先承诺高QPS。

## 5. 入口保护与可观测边界

复用已有Redis/Lua RateLimit：单活动每秒最多100次报名调用，初始保守保护值、未按真实负载定容；Redis保护失败明确拒绝受理，不旁路灌DB。每活动持久PENDING不超过1000，受理/取消/确认/失败/人工恢复同事务维护计数。单用户唯一身份限制重复资格，但重复请求也消耗入口预算；取消/结果查询不依赖该报名限流键。此版没有Redis预扣、余量缓存裁决或跨活动全站准入预算，不声称MySQL写入口已由Redis承接。

`blog.registration.events`固定stage/outcome标签记录scan/wake/publish/confirm，不使用活动ID/requestId作指标标签；请求ID仅日志关联。结果查询与管理员按状态查看请求是当前持久事实；尚无真实积压排空/延迟仪表盘或容量报告。

## 8. A2前后台业务接入（2026-10-30）

公开端`/activities`分页读取已发布活动，`/activities/:id`展示报名窗口、余量快照、纯文本说明及本人结果；动态菜单加入技术活动。活动可见不代表获得资格，浏览器按北京时间解释LocalDateTime，时间/余量仅供展示，最后裁决仍为DB。后台复用数据库动态路由和既有权限指令，组件`/activity/index`提供列表、草稿创建、开始前编辑/发布、报名状态分页、FAILED原身份恢复。不增加用户ID输入、手动改库存、重报或候补入口。

报名组件独立持有状态：按用户ID+活动ID先在localStorage保存加密随机UUID，再发送POST；网络响应未知停止提交并先查询本人结果，刷新页面或再次提交仍用原UUID。存储不可用则不发请求；没有新建身份的自动循环。登录从既有弹窗进入；切换账号、登出、路由离开都使旧响应失效。现有App使用KeepAlive，除卸载还处理deactivated，暂停计时/轮询；再次激活重新查询。

PENDING文案为“已受理，等待确认”，每次查询完成3秒后再查询，最多自动20次；失败或达到预算后停止，提供手动刷新。窗口结束不终止已受理请求的结果查询。CONFIRMED才显示成功；SOLD_OUT/CANCELED没有重新报名按钮；FAILED由管理员恢复。取消前明确提示不可重报，重复点击由busy保护，旧GET不能覆盖后发取消结果。账号隔离和请求号只是客户端接续措施，唯一约束/权限/容量仍由后端保证。

后台保存校验标题/说明、容量与未来报名窗口；响应业务失败保留表单，创建响应未知禁止在原表单再次保存，提示关闭并刷新核对，避免误点新增第二份草稿。发布/失败恢复二次确认，结果未知只刷新原事实；恢复成功仍是受理，不显示已获得名额。抽屉按状态查询，无自动全表轮询。开始后禁用编辑/发布仅作交互提示，服务端仍检查实际DB时间。

## 9. A3积压消息活性与北京时间契约（2026-11-23）

实际目标库现已执行07（备份/新连接读回见运维06第6节）；新表均空、菜单新增6条，不分配角色、不启用/部署业务。10月30日及以前的“未执行”是当时状态。

本批发现原投递协议每次扫描预约都会替换dispatch_token。若消息在broker积压超过30—300秒重投间隔，消费者拿到的前一消息可能已被下一预约作废；持续积压时反复丢弃旧代，PENDING不能保证推进。这是源码时序缺口，不冒称生产事故。

改为同一处理轮次持久代：reserveDispatch用COALESCE保留非空token，独立短事务预约后在同一请求行锁内读回实际token，再发布。每次网络发送使用独立CorrelationData ID，不能复用业务token作为多次发送的confirm身份。确认、取消、失败记录仍锁请求行；记录失败清token，下一次扫描/人工恢复才创建新代。晚到的旧失败代无权处理新代；本代重复消息允许到达，终态与事务保证业务容量只变更一次。没有延长退避去猜最大积压，也不改为无token消息或引入新平台。

实际MySQL返回session time_zone=SYSTEM、system_time_zone=UTC。JDBC serverTimezone=Asia/Shanghai用于驱动时间解释，不能代替数据库会话SET time_zone。原NOW(6)与前台ISO北京时间可能相差8小时。本域所有窗口、创建/更新时间、投递/失败到期统一引用activityNow=TIMESTAMPADD(HOUR,8,UTC_TIMESTAMP(6))；仍以数据库时钟裁决，不用JVM时钟参与余量/资格。此项只覆盖新活动域，不修改全局数据库、共享数据源或旧任务时区。活动输入/输出仍是北京时间LocalDateTime，不改前端API。目标两表刚建且为空，无历史活动时间迁移；其他库若已有旧时间数据，须先核对来源，不能猜偏移批量修正。

## 10. A4 HTTP入口与异常响应契约（2026-11-24）

真实客户端调用报名/管理接口时，身份仍只取StpUtil，匿名报名返回Result.code=402，管理权限在实际过滤器/拦截器执行。Result.flag=true且data.status=PENDING只表示受理；本批不改变唯一身份、库存事务、消息投递代、取消/恢复协议。

入口缺口：管理恢复的UUID.fromString接受短分组身份（如1-1-1-1-1），与报名DTO的标准UUID输入不一致；非法路径类型、坏JSON和方法参数约束落入系统错误；未预期异常原文直接返回前台，可能包含SQL/依赖上下文。ActivityController恢复入口增加标准8-4-4-4-12十六进制校验，合法大小写仍规范为原小写身份。GlobalExceptionHandler把ConstraintViolationException、MethodArgumentTypeMismatchException、HttpMessageNotReadableException统一返回400/请求参数不合法；未预期系统异常对外仅返回原SYSTEM_ERROR码和固定消息，完整堆栈写服务端日志。原ServiceException、IllegalArgumentException业务分支和鉴权响应保留；不宣称审计了全部业务错误文本。

采用现有MVC校验/异常处理器，未增加另一套响应封装、认证平台或前端解析规则。异常处理器为共享入口，其他控制器的同类错误也会得到固定消息，本批没有全站回归。无效输入在业务写入前拒绝；Redis限流拒绝/故障仍不旁路受理，客户端可查询本人事实并保留原requestId接续。运行时系统错误不能证明请求未提交，不能据此换号重报。

## 11. A5日志故障隔离与真实HTTP业务装配（2026-11-25）

管理创建/编辑/发布/恢复都经过OptLogAspect。该通知在服务事务提交后准备日志并调用AsyncManager调度，序列化、上下文读取或线程池拒绝抛RuntimeException时，原代码会把已提交成功改成HTTP失败；ExceptionLogAspect记录自身失败还可能覆盖原始业务异常。操作耗时ThreadLocal原先只有成功路径靠末尾remove清理，失败/提前返回会保留请求线程状态。这些是当前调用链发现的缺口，不冒称线上事故。

修正：操作日志构造/调度失败记录服务端warning，保留原业务返回；finally清理耗时，业务抛错由AfterThrowing同样清理。异常日志构造/调度失败仅告警，原异常继续交给既有全局处理器。两处参数读取允许空参数列表。仍复用原异步日志服务/表，不改事务/库存/消息协议，不新增持久审计平台，也不把日志丢失写成可靠审计。仅隔离RuntimeException，未保证JVM严重错误或日志框架自身故障可恢复；异步数据库写日志失败仍按既有线程池日志处理，不能承诺无损。

`verify_registration_dependencies.py --http --execute --expect-host <已核对主机>`新增显式HTTP模式，只选ActivityRegistrationHttpIntegrationTest，不重跑A3套件。运行器新建唯一blog_activity_<UUID>库/同名vhost，克隆2张活动表及6张角色/菜单/日志表结构，所有行均合成；Redis使用同名唯一键前缀，真实RedisConfig值序列化保持，测试BeanPostProcessor只在键序列化时加前缀。生产键名/数据库、默认开关与真实角色授权不改。SaToken会话由测试代码创建合成身份，真实StpInterfaceImpl通过实际Role/Menu XML和Redis缓存读取权限；不是密码/OAuth登录验收。

## 12. A6管理诊断与原报名恢复接续（2026-11-26）

A5实际故障处理中管理列表仅有请求号/状态/时间，无法看到发送预约、失败和下次扫描资格。本轮沿已有`GET /admin/activities/{id}/registrations`增加独立AdminActivityRegistrationVO，保留activity:registration:list权限；公开受理/本人查询/取消和管理retry仍返回原ActivityRegistrationVO，不向公开VO塞可选内部字段。

管理快照增加dispatchAttempts（数据库投递预约次数，不等于MQ发送/confirm/ACK）、failureCount（已记录的确认事务失败）、nextDispatchAt（仅PENDING时的下次扫描资格，北京时间，非保证消费或完成时刻）、failureSummary。两项次数按当前恢复轮计数，人工恢复依已有协议归零，不冒称生命周期累计。实际XML只投影所需列，不选择user_id/dispatch_token；故障摘要由last_error存在且处于PENDING/FAILED映射为固定业务提示，不原样返回数据库错误。终态即使残留时间/摘要也不对外表达成自动待恢复；无新DDL/索引/状态，无额外逐行SQL。

后台RegistrationDrawer继续负责分页/筛选/原身份恢复，RegistrationDiagnostics为只读props面板，主表“处理记录”按钮在原抽屉内展开，不新增详情弹窗、全局store或自动轮询。显示次数、精确到秒的扫描资格和安全摘要，一句必要提示区分预约/发送及恢复归零。状态变化或列表重新读取时面板派生自当前rows，不缓存旧诊断。

恢复点击时先锁本次操作并使在途旧列表响应失效，再弹确认；取消不写入。POST成功、业务拒绝或网络未知后均只GET刷新当前事实，不自动再POST；读取失败则needsRefresh保持，恢复入口禁用/列表错误可重载，成功读回才放开。FAILED按钮与原权限不变，服务端仍按当前行锁/状态裁决；页面控制不提供跨窗口/实例并发保证，也不取消已经发出的请求。网络未知不换requestId、不造新身份；读回PENDING/终态时旧FAILED操作消失。

本轮2个定向Java方法（管理HTTP权限/字段隔离、原XML解析）与实际XML SELECT临时SQLite投影/状态/过滤/分页验证通过，管理Vite产物通过。真实浏览器合成API覆盖诊断与恢复未知/成功/拒绝，不是浏览器到真实MySQL/MQ/Redis同次证据；A5真实链路独立保留、不无变化重跑。完整命令、失败修正/文件职责与剩余门槛见持续总结15第12节。
