## 1. 业务选择与范围

推荐在技术博客中增加“限量技术活动报名”：作者发布技术交流活动，设置开始/结束时间和有限名额；登录读者集中报名，查询处理结果，必要时取消。它具备秒杀的有限资源竞争、重复请求、异步处理和补偿问题，又能复用博客的用户、认证与文章入口。可以用100个名额作为受控样例，不代表实际运营数据或容量。

第一版只有活动、报名请求、结果与必要管理入口；后端优先，UI只承接受理/确认/失败状态。不引入商品购物车、支付、真实短信、营销体系或微服务拆分。首版使用现有MySQL、Redis、RabbitMQ和Micrometer。ES/Canal继续服务搜索，不用于报名名额裁决；AI处理器和AI任务表不参与报名。

## 2. 必须成立的业务不变量

| 规则 | 权威与边界 |
| --- | --- |
| 成功报名数不超过总名额 | MySQL同一事务中的条件扣减和成功记录决定；Redis余量不是最终事实 |
| 每活动每用户最多一个报名身份 | 数据库唯一约束；requestId用作重试关联，用户身份从认证取得，不相信前端userId |
| 已受理不等于报名成功 | 请求持久化后才能返回已受理；成功只在数据库确认事务完成后成立，结果可按用户/请求查询 |
| 同一请求重复处理不能多扣名额 | 对请求状态条件更新、条件扣减和结果写入处于同一个短事务；重复消息只读既有结果 |
| 必要处理可发现并恢复 | 持久PENDING请求是业务待办凭据，MQ是唤醒；进程崩溃和确认未知后可有限重投同一请求 |
| 取消只释放已成功占有的名额一次 | 取消与确认通过同一请求行状态竞争；释放库存与成功→取消转换同事务，重复取消无副作用 |
| 受理和处理时间语义明确 | 首版在活动窗口内受理，已受理请求可在结束后处理到确定结果；不保证请求到达顺序或绝对先到先得 |
| 容量故障有界 | 请求率/待处理量有预算；拒绝是明确结果；不靠无限重试或无限线程/队列假装稳定 |

首版取消后不允许同一用户重新报名，保留唯一历史身份，避免取消与新一轮抢名额的执行代复杂性。PENDING取消不回补库存，CONFIRMED取消才回补。活动名额/时间首版开始后不允许修改；主动强制关闭和通知已成功用户另设计，不能混入普通结束时间判断。

## 3. 最简单正确的第一版链路

```text
登录请求 → 活动与入口预算校验 → MySQL事务持久化唯一PENDING请求
  → 提交后尽快发布requestId（加速处理） → 返回已受理/已有结果
  → 扫描到期PENDING业务待办，带退避/上限重投，补足发布失败和进程崩溃

RabbitMQ消费者 → MySQL短事务锁定/条件认领请求
  → 已终态：返回既有结果，不再次扣减
  → PENDING：活动余量>0条件扣减 + 记录CONFIRMED，同事务提交
  → 无余量：记录SOLD_OUT，同事务提交
  → 提交完成后允许ACK；异常回滚，有限重试，失败转存/人工恢复

结果查询 → 读取当前用户自己的持久请求状态
取消 → 与确认竞争请求状态，在一个事务内转换并按需释放一次名额
```

建议数据职责为活动容量表与报名请求表：活动ID/时间/总量/余量；请求ID/活动ID/用户ID/状态/受理时间/投递尝试与下次处理时间/错误摘要。精确列名与索引实施时依现有表规范确定，提供正式SQL，不假定已执行迁移。对 `(activity_id,user_id)` 和 `request_id` 建立唯一约束；不复用AI任务表，也不为这条业务先搭通用Outbox平台。

PENDING请求即持久待办凭据；发送确认成功不意味着请求已处理，扫描恢复不能因为“发过一次”就永久忽略仍PENDING的记录。扫描按索引、批量和退避有界推进；多实例重复投递可以接受，消费必须幂等。显式记录投递失败、消费失败和业务售罄，三者不混成同一种状态。

消费者第一版只执行短数据库事务，不在持锁期间做网络或模型调用；因此不需要预设长时间RUNNING租约。请求状态与容量行采用一致的锁顺序，数据库条件更新必须检查影响行数。原子认领不是“先查状态再无条件改”。异常导致事务回滚，不能留下名额已减而请求没有成功记录。

本方案仍有每个已受理请求一次数据库持久化，不能声称整个写入口已完全由Redis承接；队列削峰的是后段容量竞争和结果处理。活动容量行可能成为热点，先用可测量的入站预算与消费并发控制，再决定优化，不能预先承诺任意吞吐。

## 4. 场景、失败和恢复

| 触发 | 应有结果 | 验证与恢复 |
| --- | --- | --- |
| 正常且有名额 | 先受理、后确认、查询到同一结果 | 数据库成功数/余量与查询一致 |
| 同用户重复点击/请求超时重发 | 返回同一报名身份，不创建第二条资格 | 两并发请求及同requestId重放；不同用户复用requestId拒绝 |
| 发布前进程退出/DB回滚 | 回滚无有效报名；已提交PENDING可发现 | 不能依赖仅afterCommit通知；恢复扫描重投 |
| broker收到但confirm丢失 | 视为结果未知，保留持久证据 | 重发同requestId，消费者不重复扣减；禁止因confirm超时直接“回库存” |
| 消费事务提交后ACK丢失 | 消息可能再投，业务效果一次 | 重复读取终态，不再次扣减 |
| 消费途中DB故障 | 扣减和状态一起回滚 | 有限重试和明确失败转存；修复后按原requestId恢复 |
| 两消费者同时处理同请求 | 一个事务产生结果，其余返回既有结果 | 真实条件更新/事务并发验证，不能仅靠Mock返回值 |
| 多用户争最后一个名额 | 最多一个CONFIRMED | 同一容量边界并发验证；余量不能为负 |
| 取消与确认/重复取消并发 | 最终取消不持有名额，最多释放一次 | 一致行锁顺序与事务；PENDING取消不增加库存 |
| 队列积压/消费暂停后恢复 | 保持已受理可查，超过预算明确拒绝新受理 | 记录最老请求年龄和排空时间；预算不是单靠队列条数实时快照保证 |
| 异常消息/故障副本无法转存 | 不伪装成功；保留待办可恢复 | 有速率限制和告警，避免故障时持续高速requeue |

首版结束后处理PENDING仍有资格争剩余名额；售罄失败为本请求终态，后续有人取消不自动把旧失败改成成功。不建立候补队列；如果以后需要候补，作为独立业务规则设计。

## 5. Redis Lua增强：基线之后再做

第一版用Redis做入口速率与重复请求加速，不把Lua预扣作为上线正确性的前提。基线正确后，可在同一报名业务增加“活动级资格预筛/预扣”实验，比较对容量行/数据库的减压效果。

Redis Lua的原子边界只覆盖脚本内Redis操作，不能覆盖MySQL与MQ。必须回答：预扣后未持久化就崩溃、MQ发送未知、同用户重试、Redis数据丢失/主从切换、旧活动预扣记录回放时如何对账。预扣与持久请求通过requestId关联，数据库唯一约束和条件容量仍是最终防线；Redis不足只能表示暂不可准入，不能未经核实宣布业务永久售罄。

持久请求之前的预扣令牌只能代表临时资格，不对外承诺已受理；失联令牌的过期/清理需要明确“未占有数据库名额”语义，不能同时补Redis和DB库存。重建需暂停相关准入或切换活动代际，按数据库已确认和在途持久请求核对，避免旧预扣/补偿写入新一代。只有协议和故障证据完成，才能称为Redis预扣闭环；不会直接照搬“DECR→发MQ→失败INCR”。
