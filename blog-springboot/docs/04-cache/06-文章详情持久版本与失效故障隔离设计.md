## 1. 问题与范围

作者编辑成功后，进程可能在afterCommit前退出，Redis失效也可能超时；另一实例可能漏收Pub/Sub通知。C2的Redis失效代仅能保护成功切代前后的装载，无法让未获知失效的L1自己知道数据库已变更。原详情逐次查可见主键，只能回答“现在是否可见”，不能回答“缓存正文是否属于当前内容”。

本切片为文章创建、文章编辑、AI摘要/建议标签写入建立持久正文标记，详情和预热共用按标记分开的缓存键。标记与正文写入同一个数据库语句/事务；读取依据数据库选版本，不以缓存删除、广播送达或Redis元数据存在为前提。独立分类/标签改名/删除尚未纳入标记，不能将此切片称作整份详情VO的完整版本体系。

## 2. 不变量与前提

1. 已采用协议的正文写入，每次产生新的不透明UUID标记，与正文一起提交。创建/编辑用应用UUID，AI结果用同一UPDATE中的数据库UUID。只比较相等，不依赖时钟精度和先后大小。
2. 详情先从当前数据库选已发布且未删除文章的版本V，再访问`article:{id}:v:{V}`。正文SQL同时约束id和V，避免新内容被错误地装载到旧版本键。
3. 装载结束后，按当前读者资格再次从数据库读取可见版本。不可见返回空；版本已变返回“内容已更新，请重新读取”；相同才构造响应并计数。负缓存也走读后检查。
4. 因此成功提交的编辑换版本后，后续选版请求不会再命中旧版本L1/L2；慢旧装载可留在旧键，但不能覆盖新版本键，也不能越过读后版本检查返回旧正文。无需对所有旧缓存做同步清理才能读新正文。
5. 权威数据库失败时不回退到旧缓存；Redis不可用时沿用现有明确失败和C1回源约束，不新增无限数据库降级。

前提：相关写入全部维护标记，数据库读取来自当前提交的权威数据，无滞后副本、提前打开的旧事务快照或旧程序写入。读后版本/可见性查询是本次返回的参考点，不能保证该检查之后到网络返回之间没有新编辑或撤回；本轮没有锁住写事务直到客户端收包。

## 3. 表字段与写入覆盖

新增`t_article.content_version VARCHAR(36) NOT NULL`，不设默认值。字段不加入ArticleVO或HTTP契约，客户端不能通过ArticleDTO指定版本。它不是乐观锁、幂等键、消息序号或任务执行代。

| 写入口 | 处理 |
| --- | --- |
| ArticleServiceImpl.addArticle | 服务端生成UUID，随insert写入；原提交后失效保留 |
| ArticleServiceImpl.updateArticle | 服务端生成新UUID，与标题/正文/封面/类型/分类ID同一updateById；文章标签保存仍在同一事务 |
| ArticleMapper.updateArticleAiResult | ai_summary、ai_suggest_tags、ai_indexed_at和UUID同一UPDATE；不把缓存故障改成模型重跑 |
| 回收/恢复、置顶/推荐 | 不改本文标记；当前状态仍由读后权威SQL裁决，置顶/推荐不在详情正文标量内 |
| 浏览量更新 | 不换版本，避免每次阅读生成新缓存键 |
| Category/Tag独立改名、删除及独立关联变更 | 尚未覆盖，C3b下一入口；编辑事务内关联变更随该次编辑的标记一起提交 |
| 原始SQL、旧程序、其他外部写入 | 不在保证内，切换时必须核实，不能凭NOT NULL推断更新方已维护标记 |

UUID不阻止旧编辑覆盖新编辑，也不阻止旧AI任务将过时摘要写回数据库；它只让读取与数据库最终已提交内容对应。编辑冲突、任务执行代和旧任务结果校验仍按后续阶段处理。

## 4. 读取、预热和旧缓存生命周期

```text
详情：DB选择已发布V（内部允许选择私人文章版本，不对外授权）
  → cache.get(article:id:v:V)
  → 缺失时C1预算/锁/C2 CAS → SQL按id和V装载
  → 读取当前读者资格 → DB按可见性取当前版本
  → 不可见：空；不同：明确重读；相同：复制VO、填导航、计数、输出

预热：DB选择已发布V → 同一个版本键 → 同一个按V约束的正文SQL
  → 无版本/无正文计skipped，异常计failed
```

初次选版使用privateAccess=true，只为选择内部共享内容版本，保持私人文章可被预热的既有规则；输出权限在装载后复用既有账号与分类/私人标签条件核实。共享缓存本身不是授权证据。预热不返回正文给用户，warmed表示观察到的版本已装载/命中，不保证其完成时仍为最新版本。

原`article:{id}`正文键不再用于新详情/预热。既有业务失效仍针对旧键，保留旧路径的尽力清理与C2行为；新版本正文的正确性依赖持久选版，不依赖旧键失效成功。旧版本正文按原Redis正/负TTL、L1容量/TTL退出，不通过KEYS扫描清理，也不为每个版本额外创建失效代。显式失效某个版本键时，manager仍按C2切代。

管理端现有evict是“删除精确key”，没有新增按articleId删除所有版本的别名；人工检查当前版本正文需使用实际版本键。clear仍只清当前实例L1，不能当跨实例全清。

## 5. 正常、故障、恢复与并发

| 情形 | 行为与边界 |
| --- | --- |
| 缓存命中、无编辑 | 前后版本一致，沿用返回/导航/统计规则 |
| 编辑提交、删除失败或漏广播 | 后续按新版本选键；旧L1即使保留也不再被该请求选择 |
| commit后进程退出 | 若正文和标记已提交，新的权威选版不依赖崩溃进程执行回调；没有建立失效待办 |
| 旧loader已读V1，编辑提交V2，新读填V2，旧loader恢复 | V1最多写V1键；读后版本V2导致旧请求拒绝，不覆盖V2 |
| 选择V1后、正文SQL前提交V2 | SQL按V1不再匹配；即使负值写入V1，读后校验仍拒绝。新请求选V2 |
| Redis丢失正文和generation | 从权威版本重新选键并按版本装载；不能因此宣布Redis整体容灾、限流/热榜/统计恢复完成 |
| 数据库故障/恢复 | 明确失败，不以旧内容兜底；数据库恢复后重新选择版本读取 |
| 撤回/私人权限收回 | 读后权限/版本查询不可见，不输出、不计数；不移除已有屏障 |
| 多次编辑、同秒写入 | 每次新UUID，无需依赖datetime秒级比较；重复编辑仍是多次业务写入，不是幂等提交 |

## 6. 选择与成本

- 选择持久标记+版本键，复用既有权威SQL与缓存管理器，隔离失效交付失败。没有添加Outbox平台、持续轮询、可靠广播组件或跨系统事务。
- 不用update_time：现有时间字段不足以保证每次内容变更可区分，AI自定义SQL也不统一维护它。
- 不按次对longtext和关联表全文计算摘要：那会把大字段读取/计算放回每次缓存命中路径。
- 不在版本冲突时自动循环重查；明确失败，下一次请求重新选版，保留C1预算。
- 相比旧详情，正常命中从1次可见性SQL变成2次版本SQL，再加原2次导航SQL，即文章Mapper同步查询从3次变4次。登录资格查询、Redis统计与逐次异步浏览量写库另计；不存在文章现在也需1次版本查询，原负缓存不再挡住这次查询。不能声称实现了“缓存命中零DB”。
- 版本越多短期正文键越多，按原TTL自然退出；没有新增后台清理任务或永久每版本元数据。真实容量、命中率与尾延迟未量化，C4必须带相同业务规则比较。

## 9. C3b正文与关联快照分离（2026-10-22，当前协议）

### 9.1 实际调用链与方案调整

CategoryServiceImpl.updateCategory和TagServiceImpl.updateTag独立更新名称，不写文章版本；deleteCategory/deleteTag先检查引用，有文章/关联即拒绝删除。检查与删除没有建立完整并发引用约束，本轮不改其写事务规则。ArticleServiceImpl.saveArticleTag在创建/编辑事务内先删再保存关系，已随文章版本一起提交。

这里无需把每次改名扇出为成批文章版本更新。那需要处理影响范围与并发新增关联，还会引入标签/分类行与文章行之间的锁顺序、失败回滚和写放大。更简单的边界是：缓存只保存由正文版本覆盖的标量，最终权威查询直接返回当前分类/标签。关系修改无需为了缓存再额外发送失效通知。

### 9.2 当前实现与业务承诺

```text
DB选择已发布版本V → cache.get(article:id:v:V:body)
  → 缺失时只按id+V读取t_article正文标量，不JOIN分类/标签
  → 获取当前读者资格
  → 一条SQL取得可见版本V'、分类、标签列表（同一数据库查询快照）
  → 无结果：空；V≠V'：明确重读
  → 复制正文VO，覆盖分类/标签，填当前读者导航，计数、输出
```

selectVisibleArticleDetailState保留PUBLIC/未删与既有私人分类/任一私人标签限制，INNER JOIN分类、文章标签和标签；与原详情一致，必须有有效分类和至少一个有效标签才返回。关联缺失不再使正文loader产生负缓存，而是在每次最终查询中抑制返回。恢复有效关联后，同一正文版本立即可被后续查询使用，无需清除正文缓存。没有新增“无标签文章可公开”的业务规则。

当改名在最终SQL开始前已提交，后续详情使用新的名称；关联删除/权限变化由该SQL重新判断。正文版本、可见性和名称列表出自同一条查询，避免分别查版本/分类/标签产生新的拼接窗口。请求复制正文后才装入本次关联对象，不改共享L1/L2，也不改其他已构造响应。关联查询失败明确失败，不回退缓存名称、不计数。

前提仍是当前提交的权威数据库、正常单条SELECT一致性、采用协议的正文写入和无陈旧外部事务快照。最终SQL之后发生的新改名/撤回无法保证从已经在途的响应中追回；允许该响应使用其最终查询时的关联快照。导航仍是随后单独查询，不能称所有详情字段来自同一个全局快照。

### 9.3 缓存结构与兼容切换

新键`article:{id}:v:{V}:body`用于详情和预热。显式articleBody结果映射仅装载正文标量，关联不在缓存中。历史articleVO组合映射已替换，避免依赖隐式映射的结构差异。

原`:v:{V}`可能因旧JOIN缺关联缓存了null；若沿用旧键，关系恢复时仍会受其负TTL影响。因此更换body后缀隔离原结构，不通过扫描清理旧键；旧正文按原TTL退出。该后缀不是再次给业务内容换版本。C3a字段迁移仍必需且未执行，本轮不增加DDL。已有article:id失效和精确key管理端语义不变，不能把evict(article:id)当成删除所有body键。

预热只预热正文，存在文章标量即可计warmed，哪怕当时没有有效分类/标签；这不代表公开可见或整份详情已预热。关联每次详情查询现取，预热不制造关联负缓存。该计数含义是C3a之后的明确调整，不把warmed当可见性保证。

### 9.4 场景与成本

| 触发 | 处理 |
| --- | --- |
| 分类/标签改名，正文版本未变，旧body命中 | 最终SQL返回当前名称，无需扇出版本或广播 |
| 关系变更、有多个有效标签 | 当前SQL快照返回当前列表，MyBatis按版本合并父记录并按标签ID组装列表 |
| 普通标签改为私人标签 | 最终SQL的NOT EXISTS拒绝普通读者，允许账号仍受PUBLIC/未删与有效关联约束 |
| 分类或有效标签缺失 | 不返回正文、不计数；后续关联恢复重新查到，不依赖负缓存过期 |
| 文章编辑与读取交错 | 最终快照版本不等于选版则拒绝，保留已有慢旧loader保护 |
| 查询异常及重试 | 明确失败；恢复后重新查询当前快照，不采用旧缓存关联 |
| 旧结构负缓存、旧缓存中的关联名称 | 新body键隔离负缓存；响应分类/标签始终用最终快照覆盖 |
| 两个读者交错构造响应 | 各自复制正文、装入各自关联/导航，不能相互污染共享正文或已构造响应 |

正常body命中仍为前置版本、最终快照、上下篇4次同步文章查询，没有新增第5次；最终SQL包含关联JOIN和权限子查询，行数随该文章标签数增加，不能因语句数相同就宣称成本相同。正文loader去掉JOIN，不再重复传输longtext到每个标签行。未度量真实DB成本、连接等待、缓存命中率或QPS，也未为这个切片增加全局信号量/线程池。C1只约束缓存重建，不能误称约束全部权威/导航查询。
