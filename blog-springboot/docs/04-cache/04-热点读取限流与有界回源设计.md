## 1. 业务触发与改前缺口

热门文章被不同读者集中访问；正文缓存缺失且持锁装载变慢，或Redis/锁依赖暂不可用。目标是正常读者不再共用文章级十次额度，竞争失败不直接扩大数据库装载压力，失败请求有明确结果且后续能恢复。

改前：Lua的ZSet成员使用毫秒时间，同一毫秒多个请求被合并计数；详情按articleId共享10次/60秒；限流返回null时会放行。cache.get等锁失败或中断后直接执行dbLoader，不同key装载也没有本实例统一并发预算。正文命中后的当前可见性、导航和统计成本另属后续切片。

## 2. 本切片不变量与权威边界

1. 每次限流调用采用独立请求成员，时间只用于score；同一毫秒不同请求仍分别计数。每个key的窗口时间以负责该key的Redis节点为准。
2. 文章详情以资源key追加访问者：登录用户使用认证ID，匿名请求使用容器解析的remoteAddr。不同登录用户的额度隔离；同一用户换IP仍共享自己的额度。
3. 仅Redis明确返回1才进入原方法；额度耗尽、结果未知或Redis数据访问失败均不绕过保护。
4. 本实例最多允许配置数量的cache.get重建请求进入等锁/装载区域。L1/L2命中不占用该预算，预热与前台缺失读取共享预算。
5. 等锁超时只再读一次L2；仍无缓存则返回繁忙。线程中断保留中断标记并拒绝，不执行备用dbLoader。
6. 预算在正常、空值、装载异常、锁/Redis异常与中断路径释放；拿到锁后的二次检查和已有空值缓存保持。
7. 当前数据库可见性屏障保持原位置和语义，不能以正文缓存命中替代权限校验。

“预算8”只指单实例的缓存重建区域，不是数据库所有SQL的全局并发上限：可见性/导航查询、浏览量更新及其他接口不在此预算内。多个实例总重建预算相加，固定锁租期到期仍可能存在跨实例重叠装载，不承诺全局只装载一次。

## 3. 限流实现与取舍

`RateLimit.perClient`默认false，保持既有AI写接口等资源级限流作用域；只在文章详情开启。详情仍为每访问者每文章10次/60秒，是沿用原额度后的作用域修正，不是经过压测校准的容量。

`RateLimitAspect`改用Spring现有StringRedisTemplate，limit/period/请求成员均按普通字符串传入，避免通用JSON序列化器给Lua参数添加类型/引号。每次调用生成UUID成员。脚本调用Redis TIME得到毫秒score，剔除窗口外成员、判断数量、插入和设置过期仍在一次脚本内完成。

使用Redis时间减少应用实例时钟差异造成的同key窗口偏移；Redis节点时间回退、集群节点间时钟与复制故障没有在本轮验证。选择滑动窗口保留现有算法，没有额外引入令牌桶平台；精确日志式窗口的存储/脚本成本仍随允许请求数增长。

匿名地址只用request.getRemoteAddr，不直接读取X-Forwarded-For等客户端可伪造头。NAT用户、反向代理后未正确恢复连接地址的访客仍可能共用额度；需要由受信代理/容器配置解决，不能仅信任任意请求头。登录用户不受匿名IP共享规则影响。本轮未调整代理或部署配置，不声称匿名用户严格一人一额度。

限流依赖失败/结果未知沿用ServiceException→Result失败契约，不返回正文。窗口拒绝提示“请求过于频繁”，依赖失败提示“访问保护暂不可用”。没有改全站HTTP状态码或所有旧AccessLimit入口；AI资源级作用域保持，但实际请求计数也受益于通用脚本修正。

## 4. 缓存重建流程与取舍

```text
L1 → Bloom辅助查询 → L2
  命中：按原逻辑返回（之后仍有业务可见性校验）
  未命中：立即尝试本实例Semaphore预算
    无预算：明确繁忙，不排入额外等待队列，不执行dbLoader
    有预算：按key等待Redisson锁
      获得锁：二查L2 → 必要时dbLoader → 原有正/空值回填
      等锁超时：最后查一次L2，命中则用持锁者结果，否则繁忙
      中断：保留标记，拒绝，不回源
    finally：释放预算
```

新增必要容量参数 `cache.multilevel.max-concurrent-loads`，环境入口 `BLOG_CACHE_MAX_CONCURRENT_LOADS`，默认8；必须大于0，否则启动失败。该值不是性能承诺，后续按连接池、查询成本与等待时间调节。原等待3秒/租期10秒保留。

采用非等待Semaphore限制不同key以及同key等锁者总量，避免增加一个无限排队层。没有新增独立线程池、分布式全局信号量或Redis故障时全量查库。锁超时最后查L2允许刚完成回填的正常请求成功，但这次额外读取本身也可能因Redis故障失败，不继续转数据库。

unlock前确认当前线程仍持锁，避免租期结束后直接解锁别人的锁。这不是fencing：租期过期的旧loader回填问题仍在，下一切片需要内容版本/失效协议。预算覆盖预热，因此预热压力可能占用前台重建槽；本轮优先统一保护回源，后续按测量决定是否需要读者优先级。

## 5. 失败、重复、并发和恢复

| 场景 | 改后结果 | 已有证据 |
| --- | --- | --- |
| 同毫秒11次请求，额度10 | 前10次进入，第11次拒绝 | 实际Lua在固定时间/受控Redis命令上执行 |
| 不同用户访问同文章 | 不同认证ID具有独立key；同用户重复请求仍计数 | 实际AOP方法+Redis调用捕获；UUID互异 |
| 匿名请求伪造转发头 | 仍按连接IP计量 | Mock请求与实际AOP方法 |
| 额度耗尽/null/依赖失败 | 业务方法不执行；下一明确允许的请求可恢复 | 隔离AOP故障注入 |
| 装载阻塞占满预算 | 其他缺失请求拒绝，不启动第二个loader；L2命中仍成功 | 真线程与CountDownLatch屏障，配置预算1 |
| 锁超时，持锁者已回填 | 最后一次L2检查成功，不执行备用loader | 控制L2返回时序 |
| 锁超时且无回填/等待中断 | 明确失败、零备用装载，中断标记保持 | 实际manager与受控RLock |
| loader/二次Redis读取失败 | 释放锁/预算，后续请求可恢复 | 故障后再请求成功 |
| 不存在内容重复访问 | 本地负缓存命中，不重复装载 | 实际manager内Caffeine与loader计数 |
| 缓存旧内容遇到撤回/账号变化 | 继续受权威校验阻断，不因保护改动绕过 | 既有ArticleServiceImplTest定向回归 |

## 7. C4a：移除无业务拦截作用的Bloom

改前`contains=false`仍读L2/DB，非空回填后再add；没有全量存在集合装载、增量修正或重建协议。正文键带持久版本，旧成员只增不减。因此Bloom并未阻挡穿透，却可在初始化、L2读取前、回填成功后因专用操作错误让请求失败。

本批删除RBloomFilter字段、初始化、contains/add与Bloom属性、YAML及.env示例入口。没有改成“Bloom未命中直接拒绝”，也不新增组件替代。manager路径现在是L1→L2→本实例预算→锁/二查→固定版本正文→失效代CAS回填。版本化正文临时缺失改为业务重读，其他通用loader仍可用空值缓存。

仅移除了源码层面的额外操作/故障依赖，没有实测Redis协议命令数、延迟或吞吐。既有Redis位图未删除，外部旧环境变量/Nacos Bloom属性不再被本实现消费；未读改实际运行配置。不再宣称Bloom过滤穿透，随机不存在ID仍可能执行初始数据库版本查询，C1预算并不覆盖该查询。新回归禁止接触getBloomFilter，并验证初始化/L2命中/冷回填与重复命中；其余原保护定向复用，完整批次见新领域文档。
