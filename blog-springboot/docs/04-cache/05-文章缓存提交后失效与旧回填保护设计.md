# 文章缓存提交后失效与旧回填保护设计

日期：2026-10-20。所属：P6-01/C2，状态为本地实现与隔离验证完成；不代表完整缓存一致性或内容版本体系已经验收。接续 [热点读取保护](04-热点读取限流与有界回源设计.md)，实际开发复盘持续记录于 [缓存阶段总结](../03-summaries/13-Phase6-缓存优化开发总结.md)。

2026-10-21接续：[持久版本与失效故障隔离](06-文章详情持久版本与失效故障隔离设计.md)已完成本地代码/隔离验证，详情与预热转为按数据库版本选键；以下保留C2交付边界。C3a迁移及真实依赖验收仍未做，旧代CAS并不自动变成整个正文版本保证。

## 1. 业务触发与改前缺口

作者编辑文章、回收/恢复或删除，普通读者和热点预热正在装载同一篇正文。原实现有两个独立窗口：

1. 写事务尚未提交就删除缓存；另一读取取得旧数据库内容并回填，作者提交成功后缓存仍旧。
2. 即使删除改到提交后，已经取到旧正文的慢loader仍能在删除之后写回；Redisson固定租期到期后，旧loader也可能覆盖另一装载者的新结果。

本实例还存在L2读取与L1安装竞态：请求取得旧Redis结果、失效通知清理L1、旧请求再把结果放回L1。只做afterCommit或只检查unlock持有者均无法消除这些窗口。

## 2. 本切片不变量与适用前提

- 通过当前manager.evict登记的数据库事务失效，只在成功提交后执行；回滚不切代、不删正文、不广播。无事务调用立即失效。
- 同一事务同一manager的多个key合并到一个回调，同key去重；某个key失效失败后继续尝试其余key，最终明确告知“内容已提交，但缓存同步失败”。数据库已提交，不能宣称因此回滚，也不能提示用户盲目重做创建/编辑。
- 每次数据库装载前读取Redis失效代。若在装载到回填之间有成功失效切代，Lua拒绝旧代回填，包括空值回填，不覆盖新值、不缓存本次旧结果，返回明确重新读取提示。不在同一次请求中无限重查。
- 对本实例已观察到的失效/clear，旧的在途读取不能在其后安装L1。Redis失效操作前后都清本地，防止操作期间开始的L2读取留下旧L1。
- 已有C1重建预算、锁竞争处理及详情数据库可见性校验保持。新建文章也登记失效，清理创建前的负缓存与旧空值装载。

前提：正文写入方调用本manager失效；Redis同时执行两key脚本且失效代保留；dbLoader读取当前提交的数据，不来自先前开启的陈旧事务快照或滞后副本。当前详情/预热调用者是普通读取，没有为本轮添加数据库长事务。不能将此协议推广到任意带事务的loader。

## 3. key、序列化与原子操作

| 数据 | key/值 | 生命周期 |
| --- | --- | --- |
| 文章正文 | `article:{id}`，沿用原RedisTemplate对象/空值哨兵序列化 | 原正值/负值TTL保留 |
| 失效代 | `cache:generation:article:{id}`，每次失效新的UUID字符串 | 不设置TTL，独立于正文过期 |
| 未切过代 | key不存在，在Java和Lua中以同一个序列化哨兵表示 | 第一次失效后转换为UUID |
| L1观察代 | 每manager的本地long，在短synchronized区读取/递增/比较 | 仅进程生命周期，不是分布式版本 |

两个Lua脚本都用现有RedisTemplate的参数值序列化器：代字符串在GET原始字节与ARGV之间直接比较；正文ARGV按原序列化写回，普通opsForValue.get仍可反序列化为ArticleVO。TTL参数为序列化Long，实际配置输出数值字节，可供EX使用；负缓存沿用原字符串哨兵。不能改用StringRedisTemplate直接序列化ArticleVO，或把JSON再次套一层字符串。

`cache_advance_and_evict.lua`：在同一个脚本中SET新失效代，再DEL正文；返回0也可能只是正文原本不存在，是成功失效。返回null代表结果未知，不能继续假装成功。

`cache_fill_if_current.lua`：GET当前失效代，比较装载前代，匹配才SET正文与TTL；比较与写入同一脚本，不能拆成应用GET后SET。拒绝返回0，Java不安装L1，也不返回旧正文。

失效代是不透明的缓存栅栏，不是t_article的业务内容版本，不表达哪次编辑较新，也不用于ES、MQ或AI结果回写。迟到的重复失效只造成额外缓存缺失，不恢复旧代。失效代不设TTL是为了避免代过期后与首次缺失状态相同的ABA问题；这会为每个曾失效key保留一个小元数据条目。不得在有在途装载时直接清理、批量过期或删除这些key。Redis全量丢失、allkeys策略淘汰元数据、旧应用直接SET正文会破坏前提，留到C3定义隔离与恢复。

当前Redisson是SingleServer，本轮脚本按单Redis节点设计；两key没有统一hash tag，不声称兼容Redis Cluster跨槽执行。迁移Cluster必须单独设计key/数据迁移与同槽策略，不在本轮引入配置或部署变化。

## 4. 读写时序

```text
写事务：更新正文/关联 → evict登记key → 数据库commit
  → 合并回调逐key执行：本地清理/递增epoch
  → Redis原子切代+删正文
  → 再次本地清理/递增epoch → 发布失效通知
回滚：不执行上述回调

读取：观察本地epoch并查L1 → L2
  → 若L2命中：本地epoch仍相同才安装L1
  → 若缺失：C1预算/按key锁 → 再查L2
  → 读取失效代g → dbLoader → Lua(g,正文/空值,TTL)
  → Lua拒绝：明确重新读取，不覆盖现有缓存
  → Lua成功：本地epoch仍相同才安装L1
```

本地epoch采用每manager一个计数，不为每个随机key维护无界对象表。任何失效都可能使另一篇文章的在途首次填充保守失败；已命中的其他L1不被清空。短同步区只操作本地内存，不持有网络/数据库调用锁。这是较简单的正确性取舍，编辑频繁时的误拒绝成本需后续观测，不假定性能免费。

Redis切代成功后、广播前存在窗口，其他实例的既有L1可能继续命中；Pub/Sub断线没有补播，C3仍开放。对于收到通知的实例，listener也推进本地epoch，防止通知前已取到的L2结果在通知后安装L1。跨实例旧DB装载的L2保护依赖Redis失效代，与是否收到广播无关。

## 5. 方案选择与失败恢复

| 选择 | 理由/没有采用的替代方案 |
| --- | --- |
| manager集中事务感知 | 覆盖现有编辑/回收/删除/置顶/推荐与管理失效，创建补一处调用；不在各业务方法复制回调 |
| 合并回调、批量尽力处理、最后显式失败 | 解决一个afterCommit异常终止后续key的问题；没有把失败静默改成成功 |
| Redis失效代CAS | 旧loader即使租期到期也不能跨成功失效回填；没有让写请求长时间等待读锁，也没有只靠双删/延迟sleep |
| 本地epoch | 阻断已观察失效后的L1安装，不引入持久本地key锁表或缓存平台 |
| 不新增数据库字段 | 本切片处理缓存失效栅栏；不是用UUID冒充业务版本，内容版本/派生结果顺序另有接续 |

成功commit到回调执行之间进程退出，没有持久失效待办；脚本发送超时可能是“未执行”或“已切代但响应丢失”；广播失败可能只影响其他实例L1。本轮不建立自动补偿或宣称可靠失效。失败有日志和“内容已提交”响应，后续可针对key再次执行evict，重复失效安全；这只是可重试操作，不是已完成的自动恢复机制。

批量失效失败时记录每个失败key，仍尝试后续key；成功key可能已生效，不能重试整个业务写入来替代缓存补偿。正文TTL仍提供部分自然过期，但不能视作明确且可靠的恢复SLA，尤其Redis旧值转入其他L1会再拥有本地TTL。

## 6. 实际验证

IDE Maven/JBR21、目标Java17：

```text
mvn -q -Dtest=CacheInvalidationConsistencyTest,MultiLevelCacheManagerTest,ArticleServiceImplTest,HotArticleWarmupServiceImplTest test
```

初次新增真实创建代理用例时，隔离MyBatis未初始化Category lambda元数据报错；按已有项目测试模式初始化TableInfo后，上述26项全部通过（新增一致性10、原缓存6、详情8、预热2）。后续新增“失效操作期间L2读取”并发时序，只重跑 `mvn -q -Dtest=CacheInvalidationConsistencyTest test`，11项通过。合计当前相关用例27项，0失败/错误/跳过，不把两次运行重复计数为吞吐或覆盖率。

关键证据：真实manager/Caffeine；两个manager对象共享受控Redis状态且不自动投递广播，真线程与CountDownLatch暂停旧loader，另一个manager切代/填新值后，旧loader拒绝且新值保留；旧L2迟到安装、远程通知、本地失效期间L2读取、负缓存与创建后恢复、回滚、提交后脚本失败不跳过其他key、广播失败/重复失效均覆盖。事务采用真实Spring TransactionTemplate/TransactionInterceptor与受控AbstractPlatformTransactionManager，实际ArticleServiceImpl创建/删除走注解事务代理；数据库Mapper/commit状态是替身，不证明MySQL隔离和真实数据库提交。

忽略target内 `CheckCacheSerialization.java` 用项目真实RedisConfig值序列化器生成失效代、ArticleVO、负值、TTL字节并反序列化验证；`check-cache-generation-lua.py` 使用已有target内Lupa执行两段真实Lua，以受控命令验证初始填充、正/负值跨代拒绝、连续切代、无正文失效、恢复、字节与TTL。命令为 `java @target/cache-c2-java.args`（指向IDE JBR和已有测试classpath）及 `python target/check-cache-generation-lua.py`。临时验证工具不增加应用依赖、不纳入提交。实际脚本执行不等于真实Redis原子性/复制或多进程验收。

Maven test编译本轮主/测试源码，没有另做发布包构建。未连接真实MySQL/Redis/MQ/ES，未启动/停止已有服务，没有多进程、压测、浏览器或上线证据，没有使用真实业务数据或付费模型。
