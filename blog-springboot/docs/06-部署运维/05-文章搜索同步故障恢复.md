# 文章搜索同步故障恢复

适用：Phase5 BD-004与Phase6/P6-02搜索恢复。2026-10-29新增可执行的受控重放客户端；离线边界验证通过，新搜索整链真实RabbitMQ验收尚未运行成功，原因和证据见第“可执行客户端”节。10月28日AI队列的真实依赖结果不能替代本链路。

## 同步与故障存储

正常入口沿用 `article.topic` → `article.key` → `article.queue`。消费者仅处理 `t_article` 的 INSERT/UPDATE/DELETE，先校验整个 `data` 的主键，再按每个主键读取 MySQL 当前行。当前 PUBLIC 且未删除时按固定 ID 覆盖 ES 文档；私密、草稿、软删除或行不存在时删除文档。

每次投递最多执行3次（含首次），间隔3秒。中间某行失败，整条消息重试；已完成的行可再次覆盖/删除。3次均失败后，将原始 body 和异常/原路由头转存到：

| 对象 | 名称 | 属性 |
| --- | --- | --- |
| 故障交换机 | `article.sync.error` | direct、持久化 |
| 故障路由 | `article.sync.error.key` | 指向故障队列 |
| 故障队列 | `article.sync.error.queue` | 持久化、不自动删除、无自动重试消费者 |

该队列是应用确认转存的故障队列，不依赖原队列的 DLX 参数。`article.queue` 的既有参数不变，避免上线时因新增队列参数触发 `PRECONDITION_FAILED`。

原消息仅在处理成功或故障副本收到 publisher confirm 且未被 mandatory return 时允许正常确认。NACK、连接异常、确认等待超时或无路由，均抛出 `ImmediateRequeueAmqpException` 保留原消息。转存确认最多等待10秒。网络不确定和进程退出可能产生重复副本，采用至少一次处理语义，不承诺恰好一次。

若故障存储自身持续不可用，原消息会跨投递再次尝试，3次限制仅针对每次投递，并非总生命周期；这是一种保留数据的故障状态，不算恢复成功。通过错误日志、主队列积压和故障队列积压定位，需恢复 MQ/路由后接续。

## 接入前确认

应用数据源必须与 Canal 监听的业务库一致；Canal 应发送完整 JSON，包含 `table=t_article`、DML type、每行主键。`es` 按 Long 接收13位时间戳，不能当成业务版本。当前消费者没有多业务数据库路由能力。

有效配置必须保留 `spring.rabbitmq.publisher-confirm-type=correlated` 和 `publisher-returns=true`。应用中搜索专用模板启用 mandatory；不新增全局 RabbitTemplate/MessageRecoverer bean，以免改变邮件、AI 等消费者的模板与恢复器选择。Nacos或私有配置覆盖这些属性时，需要核对最终生效值。

部署前在隔离环境确认新交换机、队列、绑定可声明，账号有相关权限；注入 ES 写入失败后，核对原始消息进入故障队列。移除故障路由后验证原消息重新投递，再恢复路由验证可转存。此步骤尚未执行；单测中的 broker confirm/return 为受控桩。

## 故障处理与重放

1. 观察异常原因与故障队列原始 body；区分 ES不可用、数据库读取失败、文档映射/索引缺失、消息缺主键等原因。不可把队列清空当作修复。
2. 先恢复依赖或修复格式。对于坏消息，根据原始数据库事实重建正确的文章 ID 批次，保留原故障凭据；不能将不相关消息强行改成文章事件。
3. 使用支持手动 ACK 与 publisher confirm 的消费/发布客户端，从故障队列逐条获取并保持未确认，将原始 JSON body 持久化发布回 `article.topic`、路由 `article.key`。确认发布 ACK 且没有 return 后，才 ACK 对应故障消息；失败则保留/重新入队。不要使用“读取即自动确认”导出后再发送。
4. 先选一个小批次验证：数据库最新文章与索引标题、正文、状态一致，已删除/非公开文章索引不存在；等待 ES refresh 后再检索验证。恢复流量没有在代码中自动放大为全库重建。
5. 确认故障队列下降、没有相同原因继续积压。新消息仍可能失败后再次转存，因此转发成功只表示重新进入处理链，不等于索引同步完成。

首轮只提供消息保留机制和人工重放协议；2026-10-29已补下节的一次性重放客户端，不自动回灌，不增加HTTP端点/界面或定时全量任务，尚未对现有真实故障队列执行读写。

## 保证边界

重放按数据库当前状态同步，避免直接把旧事件中的正文写回。若两个实例分别读取新旧行后乱序向 ES 写入，仍可能发生旧结果覆盖；解决该问题需后续内容版本/条件写入设计。`es` 时间戳和单实例消费者数量不能替代该保证。

公开访问继续使用当前权威可见性校验（后续批次已覆盖私人标签/分类），尤其在缓存和ES延迟期间，不能靠MQ重放替代。该链路不承诺所有在途响应即时撤回，不修复历史已经丢失的所有事件，也不把队列持久化/确认当作集群灾备证明。

2026-10-17接续：详情与搜索出口已增加当前数据库PUBLIC/未删状态读取屏障，见 [读取校验设计](../01-架构设计/02-公开文章撤回读取校验设计.md)。该保护以状态SQL快照为界；没有消除ES并发乱序、主从延迟或SQL之后撤回的在途响应，也没有完成真实MQ/MySQL/ES联调。

## 可执行客户端（2026-10-29）

代码：[replay_article_search.py](../09-模板与脚本/replay_article_search.py)。定位是ES/数据库故障排除后的运维恢复工具，不是单测脚本或第二套消息平台。凭据通过当前进程环境传递：`BLOG_RABBITMQ_HOST`、`BLOG_RABBITMQ_PORT`（默认5672）、`BLOG_RABBITMQ_VIRTUAL_HOST`、`BLOG_RABBITMQ_USERNAME`、`BLOG_RABBITMQ_PASSWORD`。不自动加载.env/私有YAML，防止无意选择业务vhost；应由已授权本地配置/密钥工具注入最终生效值，不能把密码写在命令行、报告或Git文件中。项目已有target/q4-python中的pika1.3.2可复用。

工作目录blog-springboot；下列HOST和VHOST需替换为已核查目标，不是默认生产地址：

```text
python docs/09-模板与脚本/replay_article_search.py --expect-host HOST --expect-vhost VHOST
python docs/09-模板与脚本/replay_article_search.py --expect-host HOST --expect-vhost VHOST --execute --limit 1
```

第一条只被动检查既有故障队列、目标队列/交换机并返回ready数量，不basic_get、不发布、不改变拓扑。被动存在性检查不证明绑定正确，执行前仍需核对article.key→article.queue绑定；mandatory只证明至少一个队列可路由，不证明目标消费完成。第二条显式执行，默认最多1条，可指定1—100条；逐条处理且遇首个失败立即退出。主机/vhost必须与环境完全一致。故障队列有活动订阅消费者时拒绝；basic_get客户端不计入consumer_count，因此这不是分布式互斥，操作员仍需串行执行，重复语义不变。

每条流程：手动ACK获取→整批文章DML/所有正整数32位主键校验→落盘审计→原字节body持久化mandatory发布到固定article.topic/article.key→收到confirm且无return→落盘确认阶段→发送原故障消息ACK。只允许t_article的INSERT/UPDATE/DELETE，整批任一主键坏都不发布任何行，不跳过、不改正文、不吞掉坏消息。原消息正文/错误上下文保留；不携带旧expiration和user_id，避免修复后重发立即过期或被原发布身份限制拒绝。已有message_id保留，无ID时使用正文SHA256，但这仅供关联，不构成broker去重。

NACK、return、连接未知、审计失败或坏消息：不再获取后续消息，关闭连接使尚未ACK的来源恢复。确认后、源ACK前中断会留下目标消息和原故障消息，再执行可能重复；ACK本身没有broker回复，`source_ack_sent`只记录发送，不承诺删除确认。`publish_confirmed`只代表重入MQ，`index_completed=not_checked`明确不表示ES同步完成。仍需观察消费者失败是否再入故障队列，并比对当前数据库与索引。

每次执行审计在Git忽略`logs/search-replay/<UUID>.jsonl`，逐阶段flush/fsync，记录时间、正文哈希、文章ID、原消息ID和计数，不写正文/凭据。不能在校验/确认阶段用丢失的审计当成功；审计盘本身故障可能无法记录最终停止事件，优先保留未确认来源。已发送源ACK之后的审计失败仍可能已移除来源，应结合确认记录核查，不能强行回滚这个网络事实。

BlockingChannel的socket_timeout不等于publisher-confirm总期限，命令由单独子进程执行、父进程120秒超时终止；超时报告delivery_outcome=unknown，不能自动重跑或认为消息未发出。进程/主机被强杀不能保证finally执行，未ACK由broker在连接失效后恢复；用审计定位，不清空队列。客户端不做自动重试、不增加服务器队列TTL、不修改服务端配置。
