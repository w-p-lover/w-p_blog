# 缓存体系审计与改造方案

## 1. 文档目的

本文用于承接第二阶段开发前的缓存体系审计，先客观梳理当前 `blog-springboot` 中 Redis、多级缓存、限流、热点文章预热和缓存管理能力的真实状态，再给出第二阶段的开发边界。

第二阶段不直接重写所有 Redis 调用，而是围绕文章主链路先做可控深化：

- 建立缓存体系的文档分类和审计基线。
- 将热门文章从浏览量排序升级为文章热度分模型。
- 使用 Redis ZSet 维护可解释的热榜。
- 用热榜驱动热点文章缓存预热。
- 补充缓存治理所需的 key 规范、日志、指标和测试。

## 3. 当前缓存体系客观评价

### 3.1 已经具备的能力

当前项目不是简单 Redis 缓存，已经具备较完整的缓存雏形：

- 文章详情已经接入 `MultiLevelCacheManager`。
- 本地 L1 使用 Caffeine，远端 L2 使用 Redis。
- 使用 BloomFilter 辅助处理缓存穿透。
- 使用 Redisson Lock 处理热点 key 击穿。
- 使用空值缓存降低不存在数据的反复回源。
- Redis 缓存写入带随机 TTL，降低雪崩风险。
- 通过 Redisson Topic 做多实例 L1 失效通知。
- 文章详情接口接入 `@RateLimit`，使用 Redis Lua 做滑动窗口限流。
- 文章浏览量、点赞量、访客量等高频数据已经放入 Redis。
- 已有 `CacheController` 提供基本缓存管理入口。
- 已有 Micrometer 指标基础，文章浏览量已经可以进入 Prometheus。

这些能力说明项目已经从“手写 Redis get/set”进入了“多级缓存基础设施”的阶段。

### 3.2 当前主要问题

当前缓存体系的短板不在于没有 Redis，而在于治理边界还不清晰：

1. 缓存职责分散  
   `MultiLevelCacheManager` 主要服务文章详情，其他业务仍直接使用 `RedisService`。站点配置、点赞、访客、限流、Sa-Token 都使用 Redis，但没有统一分类说明。

2. Redis key 管理仍偏常量堆叠  
   `RedisConstant` 里有 key 常量，但缺少 key 命名规范、业务类型、TTL 策略、是否允许手动删除等说明。后续 key 越多，排查和治理成本会升高。

3. 热点文章仍主要依赖浏览量  
   当前热点预热逻辑主要看 `ARTICLE_VIEW_COUNT` 和置顶状态，缺少点赞、评论、收藏、推荐、发布时间衰减等综合热度模型。

4. 预热触发位置偏业务列表查询  
   当前 `listArticleHomeVO` 查询文章列表后异步预热候选文章。这个方式能工作，但它依赖用户访问首页触发，不是独立、可观测、可手动补偿的预热任务。

5. 缓存管理接口表达不够精确  
   `CacheController.clear()` 实际只清 L1 本地缓存，但接口文案容易被理解成清空全部缓存。后续需要区分 L1 清理、L2 key 删除、热榜重算、热点预热。

6. 限流体系存在两套实现  
   `@RateLimit` 使用 Redis Lua 滑动窗口，`@AccessLimit` 使用拦截器和简单计数。二者可以并存，但需要文档说明适用场景，避免后续重复建设。

7. Redis 启动修复需要明确边界  
   `RedisStartupFix` 会尝试执行 `CONFIG SET stop-writes-on-bgsave-error no`。这是运维修复手段，不应该被误解为缓存业务逻辑，建议后续配置化开关或至少写入运维说明。

8. 收藏统计存在字段命名需要核实  
   `UserFavorite` 实体使用 `favoriteId`，但 `UserFavoriteMapper.xml` 仍使用 `doc_id`。第二阶段若纳入收藏权重，需要先基于现有表结构确认字段含义，避免误把文档收藏当文章收藏。

## 4. 第二阶段推荐方案

### 4.1 推荐方案

推荐采用“缓存审计先行 + 热度分系统 + 热点缓存预热”的方案。

这个方案的核心不是重写整个缓存体系，而是在已有多级缓存能力上补一条高价值主链路：

```text
文章统计信号
    -> 热度分计算
    -> Redis ZSet 热榜
    -> 热点文章缓存预热
    -> 首页和后台热榜读取
    -> 日志、指标、测试、文档沉淀
```

### 4.2 暂不推荐的方案

不建议第二阶段直接做“全站 Redis 重构”。

原因：

- Redis 已经被权限、限流、统计、站点配置、点赞集合、文章缓存多处共享。
- 一次性重构所有 Redis 用法风险大，容易引入行为回归。
- 当前最能体现后端深度的是文章热度分和热点缓存预热，它能连接 Redis ZSet、多级缓存、定时任务、指标和文档，范围更可控。

也不建议只做“新增热门文章接口”。

原因：

- 只新增接口无法解决缓存治理问题。
- 如果仍然只按浏览量排序，和当前系统相比提升有限。
- 面试表达上缺少系统设计深度。

## 5. 第二阶段设计目标

### 5.1 热度分模型

新增文章热度分，基础模型为：

```text
hotScore = viewCount * viewWeight
         + likeCount * likeWeight
         + commentCount * commentWeight
         + favoriteCount * favoriteWeight
         + recommendWeight
         + topWeight
         - timeDecay
```

建议默认权重：

| 信号 | 默认权重 | 说明 |
|---|---:|---|
| 浏览量 | 1 | 低成本弱信号 |
| 点赞量 | 5 | 用户主动反馈 |
| 评论量 | 8 | 互动成本更高 |
| 收藏量 | 10 | 长期价值更强，初版可在字段核实后接入 |
| 推荐 | 30 | 运营权重 |
| 置顶 | 50 | 强运营权重 |
| 时间衰减 | 每天 1.5 | 防止旧文章长期霸榜 |

收藏数据如果字段含义未完全确认，第一版可以将 `favoriteCount` 作为可选信号：先保留模型和测试，代码中通过 mapper 明确限定文章收藏类型后再启用。

### 5.2 Redis 热榜

新增 Redis ZSet：

```text
blog:article:hot_score
```

约定：

- member：文章 ID。
- score：文章热度分。
- 写入方式：定时全量或增量刷新时使用精确分数写入，不使用累加写入，避免重复刷新导致分数膨胀。
- 读取方式：`ZREVRANGE` 或 `reverseRangeWithScores` 获取 Top N。
- 生命周期：热榜 key 可以长期存在，由定时刷新覆盖分数。

### 5.3 热点缓存预热

新增热点缓存预热能力：

```text
读取 blog:article:hot_score Top N
    -> 查询文章详情
    -> 通过 MultiLevelCacheManager 写入 article:{id}
    -> 记录预热数量、耗时、失败原因
```

预热不应依赖用户访问首页触发，应支持：

- 定时任务触发。
- 管理接口手动触发。
- 热度分刷新后自动触发。

### 5.4 缓存 key 规范

第二阶段建议先引入轻量 key 规范，不做大规模迁移：

- 保留现有 `RedisConstant`，避免一次性影响所有业务。
- 新增或补充明确常量：
  - `ARTICLE_DETAIL_PREFIX = "article:"`
  - `ARTICLE_HOT_SCORE = "blog:article:hot_score"`
  - `ARTICLE_HOT_WARMUP_LOCK = "lock:article:hot:warmup"`
  - `ARTICLE_HOT_REFRESH_LOCK = "lock:article:hot:refresh"`
- 文档中给出 key 分类：
  - 业务缓存：文章详情、站点配置。
  - 统计计数：浏览量、点赞量、访客量。
  - 用户集合：用户点赞集合。
  - 限流 key：接口限流和访问控制。
  - 基础设施 key：布隆过滤器、分布式锁、Topic。

### 5.5 指标和日志

建议补充以下信息：

- 热度分刷新文章数量。
- 热度分刷新耗时。
- 热点预热文章数量。
- 热点预热失败次数。
- 热点预热跳过原因，例如热榜为空、文章不存在、缓存已命中。

指标可以复用现有 `BlogMetrics` 扩展，命名示例：

```text
blog.article.hot_score.refresh
blog.article.hot_cache.warmup
blog.cache.hot_article.warmup.failures
```

### 5.6 管理接口

当前 `CacheController` 已经存在，第二阶段可以在其基础上补充管理能力：

- 查询 L1 统计。
- 手动刷新文章热度分。
- 手动预热热点文章。
- 查询当前热榜 Top N。

接口命名建议保持在 `/admin/cache` 下，避免新增分散控制器。

## 7. 测试策略

第二阶段必须补测试，不能只靠手工验证。

### 7.1 单元测试

重点覆盖：

- 浏览、点赞、评论、推荐、置顶、时间衰减下的热度分计算。
- 精确写入 Redis ZSet，不使用增量叠加。
- 热榜为空时预热任务不报错。
- 热榜含失效文章时跳过并记录日志。
- `CacheController` 调用 service，不直接访问真实 Redis。

### 7.2 Spring 上下文测试

继续保持第一阶段修复后的原则：

- 测试 profile 不依赖真实 `.env`。
- 测试不连接真实 Redis、RabbitMQ、Qdrant、数据库。
- 外部依赖通过 mock 或 test profile 隔离。

### 7.3 完整回归

每次阶段完成后必须运行：

```powershell
mvn test
```

通过后再提交和合并。

## 8. 验收标准

第二阶段完成后，应满足：

- 新增 `03-缓存体系` 文档分类。

## 9. 后续暂缓项

以下内容有价值，但不建议放进第二阶段第一版：

- 全站 Redis key 注册中心彻底替换所有 `RedisConstant` 使用。
- `article_hot_snapshot` 每日快照表。
- 基于 Testcontainers 的真实 Redis 集成测试。
- 统一替换 `@AccessLimit` 和 `@RateLimit`。
- 将 Sa-Token Redis DAO 纳入统一缓存治理。
- 把所有点赞、评论、收藏统计统一抽象为事件流。

这些更适合放到后续“缓存治理体系”或“Testcontainers 与 CI”阶段。

## 10. 面试表达

完成第二阶段后，可以这样表达：

> 我先对项目已有缓存体系做了审计，区分了多级缓存、Redis 计数、限流、权限存储和热点预热等不同职责。随后围绕文章主链路设计热度分模型，综合浏览、点赞、评论、收藏、推荐、置顶和时间衰减，使用 Redis ZSet 维护热榜，并用热榜驱动热点文章缓存预热。这样热门文章不再只是按浏览量排序，缓存预热也从被动触发升级为可配置、可观测、可手动补偿的治理能力。
