## 1. 业务触发、权威与承诺

热门文章正文已经命中，但请求仍单独查询上下篇、Redis先读后加，每次阅读提交一项数据库更新任务；首页每次请求又为全部匹配文章提交预热。运营刷新热榜时，先删除正式榜单，再逐篇写入，失败或并发时可能读到空榜、半榜或被旧刷新覆盖。组件接入并不等于完整链路已经减压。

本批承诺限于：

- 当前版本、权限、分类/标签、上下篇来自返回前同一个数据库语句；正文仍按持久版本取缓存。导航保留既有PUBLIC、未删和私人内容排除规则，不放入共享正文缓存。
- 展示型PV每次可读请求尝试计一次，重复刷新也计数；它不是UV、实际读完、浏览器已收到响应或审计账本。正常Redis状态下，计数、待同步登记和返回累计值在一个Lua内完成，不再返回“先读旧值+1”的并发旧数。
- 数据库只接受累计高水位快照，重复/乱序同步不增加第二份，也不回退已持久化数值。新阅读发生在快照之后，旧ACK不能清掉其待同步资格。
- 热榜读者看到上一次完整榜或本次完整榜；正常查询确认的空集合才发布空榜。旧执行不能越过更新执行的刷新代发布。
- 选版本后撤回/删除造成的临时正文缺失不产生新负缓存；同版本恢复不需要等待这类负缓存TTL。

没有承诺整接口脱离Redis、精确一次PV、全局只装载一次、无损统计或生产吞吐。所有事实依赖C3a字段迁移、所有应用统一版本、数据库主库/有效新快照及当前单Redis服务端脚本原子边界。

## 2. 详情查询与动态统计隔离

`selectVisibleArticleDetailState`在原有快照中增加DB的`views`、按小于当前ID取最大可见ID的上一篇、按大于当前ID取最小可见ID的下一篇。导航通过LEFT JOIN和嵌套resultMap映射，缺失一侧用`notNullColumn`保持null，多标签行仍只生成一个父快照。两个导航候选分别应用现有私人规则，不依赖正文缓存的账号上下文。

正常正文L1/L2命中的独立同步文章SQL由4次变为2次：初始版本、最终快照。冷回源另有一次固定版本正文SQL；登录身份解析的查询另计。最终SQL内部仍做上下篇查找和关联JOIN，标签行重复携带导航列；减少网络往返不等于内部扫描消失或总DB成本已经量化。未执行真实MySQL EXPLAIN/索引/尾延迟验证。

正文loader不再读取/缓存动态统计。最终授权和版本一致后，才调用PV服务并读取点赞。PV的Redis数据访问异常或结果未知返回最终DB快照的views，点赞数据访问异常返回0并记录失败指标，不阻断已经通过权威校验的正文。入口Redis限流、L2、锁、广播仍可能拒绝请求，不能把这项降级描述为完整Redis故障可用。

选版本后正文SQL返回null直接抛“内容已更新，请重新读取”，manager不会把它写成负缓存；预热采用相同规则。如果命中升级前body负缓存而最终权威快照确认当前版本存在，详情清除该body键并明确要求重读，下一请求重新装载；清除失败则继续明确失败。初始未发布/已删仍直接返回null，最终不可见也不输出正文。通用manager对其他loader保留空值缓存。

## 3. PV累计值、待同步与恢复协议

复用`article_view_count`的ZSet累计值，新增`article:view:pending`ZSet，member都是十进制文章ID，与原Integer JSON成员兼容。pending的score记录首次待同步时间，高频阅读不反复排到队尾。两键不设过期；它是Redis中的待同步证据，不是独立于Redis的持久账本。

```text
权威快照确认可读且版本相同
  → Lua检查两键类型
  → total = min(max(Redis累计值, 当前DB快照views) + 1, INT_MAX)
  → 写累计值 + ZADD pending NX首次时间 → 返回同一次递增结果

应用内调度每次完成后再等30秒，首次延后30秒
  → 单次Lua按首次待同步顺序取最多100篇及其累计值
  → 每篇单条SQL：views = GREATEST(COALESCE(views,0), snapshot)
  → SQL调用成功返回后，Lua比较当前累计值是否仍等于snapshot
      相同：移除pending；已出现新阅读：保留pending
  → 某篇失败不阻断本批其他篇；下一轮仍从pending取得失败/新阅读项
```

`@EnableScheduling`启用调度，使用项目已有可用的调度执行器，不依赖手工增加Quartz数据库任务。没有每PV的线程任务、消息或DB写入；后台至多100篇/轮/实例，每篇独立SQL，未声称一条批量SQL处理100篇。30秒/100篇是当前明确基线，不是经压测校准的容量。若待同步文章超过处理能力，滞后会超过30秒，不能宣传“最多丢30秒”。多实例可同时同步同一快照，DB高水位和ACK比较容忍重复，但会产生重复SQL，未加通用分布式调度平台。

| 触发 | 结果与恢复 |
| --- | --- |
| 同文章并发/重复刷新 | Lua串行递增，不是旧值各自加一；每个刷新独立计PV，无请求幂等身份 |
| Redis递增响应丢失/null | 不重试该次增量，返回DB快照；可能已计入待同步，不承诺这次一定未计数 |
| DB失败或写入成功但回复丢失 | 不ACK，重试同一绝对快照；GREATEST不会再加一份 |
| DB提交后进程退出或ACK丢失 | pending可能仍在；重复同步绝对值安全，若ACK已完成则DB已写成功 |
| 快照100后新阅读到101 | 写100后ACK比较失败，pending留下；后续写101 |
| 两实例或乱序写100/101 | DB不回退，旧ACK不会移除101的未同步标记；允许冗余工作 |
| 文章已物理删除 | UPDATE影响0行也可ACK，不重建文章或无限保留无对象统计任务；假定主键不复用 |
| Redis总数/待同步数据丢失或回滚 | 未同步PV可能丢失；当前DB值只提供重建下限，后续请求重新计数，无法追回已丢增量 |
| Redis计数键单独被清理，pending残留 | 快照脚本移除无累计值的孤立标记；这不是找回丢数 |

统计可少计：Redis数据丢失、依赖失败、Lua/网络结果未知及恢复期间与并发checkpoint重叠均有边界；不提供严格丢数上限。SQL是高水位而非增量，DB已成功值不会由本协议降低。没有事务跨MySQL和Redis、AOF/RDB/复制验收或失败时转生产写库。PV有INT_MAX饱和上限，匹配现有Integer/数据库字段，不额外引入BigInt迁移。

已有`RedisStartupFix`在应用启动时尝试禁用服务端RDB失败写保护，这是现有运行配置风险，本批未改该类，不能据此把Redis待同步证据称为已落地的持久可靠存储。下一缓存批次会处理该自动修改服务端配置的行为；本轮未启动应用或实际执行CONFIG SET。

## 4. 热榜分批构建、原子切换与刷新代

仍用原权重/衰减公式、原来源查询和正式`blog:article:hot_score`键，没有重建热榜产品。刷新开始、读取DB/Redis各信号之前，把随机UUID写入正式键的`:refresh`伴随键。每次刷新使用唯一`:build:{UUID}`临时ZSet：每批最多100篇，Lua先核对刷新的UUID，再校验分数、构建临时键并设120秒TTL。未修改正式榜单。

所有候选构建完成后，发布脚本再次比较刷新代和临时键ZCARD：

- 非空且数量正确才RENAME至正式榜单并PERSIST，避免临时TTL随RENAME带到正式键。
- 空集合仅在所有查询正常返回后明确DEL正式榜；查询异常不进入发布。
- 被更新执行替代、临时键过期/不完整、未知结果均明确失败，保持已有正式快照。普通finally只清临时键；清理失败记录日志并依赖TTL，不把已成功发布改报失败。

最新“开始的刷新”获发布资格，不等于所有信号同一事务快照。后开始执行若失败，前一个在途执行也被其替代，正式榜继续保留上次完整版本，下一次成功刷新恢复。并发或定时重复触发不保证只读一遍DB；UUID是发布栅栏，不是互斥锁。进程/Redis故障、复制回滚与脚本运行时错误不具有跨系统回滚保证。临时键TTL是有限清理机制，不是保证120秒内刷新一定成功。

当前配置为Redisson单服务端模式，PV/热榜的多键脚本没有Cluster哈希槽协议；不宣称已经支持Redis Cluster。热榜仅是派生候选，最终详情继续执行当前权威校验，榜单并不是公开内容权限依据。

## 5. 首页预热的范围与重复工作

首页只对当前返回页做原有内容/标签处理和热候选识别，不再对全部匹配文章触发预热。同一实例`AtomicBoolean`把一个首页预热任务从排队到执行结束合并；重复首页请求在此期间不再提交同类任务。任务异常或提交失败释放标记并记录日志，后续首页请求能重试。

这是本实例的可省略优化，不是持久业务待办。某一页的候选可能在另一页预热运行时被跳过，正文请求仍正常按需加载；后台/管理员的显式预热仍走原流程，多实例不做全局预热去重。预热复用版本化body和原C1有界回源，不强刷有效缓存、不承诺热榜前N篇必然全在缓存。首页原始全量SQL/内存分页及全量PV ZSet读取仍存在，没有把候选范围收窄描述成整个首页容量治理已完成。

### 7.2 指标的范围和精确定义

| 指标 | 固定维度/结果 | 含义与限制 |
| --- | --- | --- |
| `blog.cache.events` | `stage=request`，`outcome=value/null/error` | 一次manager.get的最终结果；不代表完整HTTP详情请求通过权限校验或浏览器已收到 |
| 同上 | `l1`：`hit/negative/miss`；`l2`：`hit/negative/miss/error` | L1按入口一次；L2按实际Redis读，包括锁内二查和超时后末次读，不能把L2次数当请求数 |
| 同上 | `budget/rejected` | 本实例重建预算未取得，未执行loader；L1/L2命中不占预算 |
| 同上 | `lock_create/error`、`lock_wait/acquired/timeout/interrupted/error`、`lock_release/error` | 区分创建/等待/中断/释放失败；超时后可能读到获胜者L2值，timeout不等于整个请求失败 |
| 同上 | `generation_read/error`；`loader/value/null/error` | loader错误包括业务版本变更主动拒绝，不能全部算数据库故障 |
| 同上 | `fill/accepted/stale/unknown/error`；`local_fill/stale` | Lua返回1、非1、null、异常及L1 epoch拒绝；unknown/异常可能Redis已经执行，均不安装成功L1或直接返回刚装载值 |
| 同上 | `evict/applied/unknown/error`；`publish/sent/error`；`subscribe/error`；`notification/received` | 删除返回0仍是正常执行（正文原本不存在）；发布完成包括0订阅者，绝不表示远端已收到。收到也不表示其他实例全部收到 |
| `blog.cache.duration` | `stage=request/lock_wait/loader` | 每段实际调用完成耗时，包含运行时异常和锁中断；不是端到端接口延迟，未新增直方图或声称已有P99 |
| `blog.cache.rebuild.active` | 无业务标签 | 当前实例已取得预算、正在等锁/装载/回填/释放的调用数；含预热，不含命中或manager之外的初始/最终权威SQL。当前容量来自`cache.multilevel.max-concurrent-loads`，默认8 |

所有新增缓存标签仅由调用点固定字符串产生，不含articleId、cache key、用户或异常文本。按现有Actuator/Micrometer入口暴露，未新建管理API或看板，未在实际HTTP/Prometheus环境验证采集。原有按articleId的PV指标没有在本批顺手重构；新增有限标签不等于全系统指标已无高基数风险。

排查先看`request/error`与budget/lock/loader/dependency分段：预算拒绝且active持续接近本实例配置值时，结合锁与loader耗时定位等待或慢装载；`l2/error`、generation/fill/lock错误说明相应依赖操作失败，不通过自动查库放大压力。`fill/stale`与`local_fill/stale`说明并发保护发生，不应都当Redis宕机。evict/publish错误需结合“数据库可能已提交”的日志处理，不让用户反复保存来假装回滚；正文按持久版本选键的保护仍依赖主库/新快照。未预设告警阈值或凭默认预算推算系统容量。

恢复依靠后续正常请求、既有持久版本选键或显式重试原失效操作；指标不执行补偿、不新增持久失效待办。锁释放异常原来就会向外抛出且可能遮盖loader异常，本批仅区分计量，不宣称锁释放故障已容错。固定租期不保证全局只装载一次；版本/失效CAS负责相应陈旧值保护。
