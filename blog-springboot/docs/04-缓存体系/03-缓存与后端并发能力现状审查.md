## 2. 缓存真实读取链路

```text
文章详情入口的资源级 Lua 限流
  → MultiLevelCacheManager
      L1 Caffeine 命中 → 返回缓存对象
      L1 未命中 → Bloom contains（不拒绝）→ Redis L2
      L2 未命中 → Redisson 按 key 加锁 → 再查 L2 → DB loader → 回填
      锁等待失败/中断 → 直接 DB loader
  → 当前账号资格解析
  → DB 当前可见性校验
  → 复制响应对象 → DB 上一篇/下一篇查询
  → Redis 浏览量读取/递增、点赞读取
  → hotArticleExecutor 为每次阅读提交一次数据库浏览量更新
```

入口：`ArticleServiceImpl.getArticleHomeById`、`updateArticleStatsFromRedis`；核心：`MultiLevelCacheManager.get`。空值命中直接返回，不经过后面的非空文章处理。

非空且当前可读的 L1 命中请求仍有三次文章 SQL 读取（可见性、上一篇、下一篇）、一次异步 SQL 更新，以及 Redis 和限流访问；登录账号解析还可能增加用户查询。L1 命中节省的是正文装载等工作，不是整个 HTTP 请求的数据库和 Redis 成本。不能拿单独 Caffeine get 的吞吐量代表详情接口能力。

可见性查询是 Phase5 撤回保护的一部分；不能为了压测数字将其删除。应先区分正文、当前权限、个性化导航与统计各自的时效要求，再削减可以安全合并或延迟的工作。

## 3. 已有优点、实际缺口和推荐处理

| 主题 | 已有优点 | 源码缺口及业务后果 | 推荐处理 |
| --- | --- | --- | --- |
| L1/L2 | Caffeine 限容量与过期，Redis 共享正文；减少重复装载 | L1 命中仍执行上述 SQL/Redis；缓存命中率不等于整链路提速；maxSize 按条数不按字节 | 测量完整请求成本，拆出各类读取预算，再考虑导航/统计优化 |
| 空值缓存 | 同一个不存在 ID 反复请求时减少装载 | 随机不同 ID 的首次请求仍可回源；空值与正值 L1 使用同一过期策略 | 入口校验与有界回源共同保护；新建/恢复后的负缓存失效也需明确 |
| Bloom | 未命中不直接拒绝，避免未初始化/新记录被误拦 | `contains=false` 仅记日志，仍读 Redis/DB；不能算有效的穿透拦截。成功回源才 add，本轮没发现完整存在集合装载 | 若没有可维护的权威存在集合，优先移除无效热路径成本；若保留拦截，先定义初始化、增量和故障策略 |
| 回源锁 | 按文章 key 锁，获取后再次检查 L2，能够合并正常竞争下的装载 | 等待失败/中断全部回源 DB，热点慢请求时可放大数据库压力；没有有界降级。固定 lease 到期后慢装载可能继续回填，unlock 也可能失败 | 用有界等待/本进程请求合并/回源并发预算约束压力；锁与版本校验解决不同问题，不能仅加长租期 |
| TTL | 正值 Redis TTL 加随机抖动，分散部分同时到期 | 抖动不解决单一超级热点；L1/L2各自过期，L2到期前转入L1仍可再保留一个L1周期 | 写明允许旧值窗口、正文版本与权限时效；不要将所有TTL问题统一称为雪崩 |
| 多实例失效 | 删除本地、Redis并发布 Redisson Topic 消息 | Pub/Sub 无持久重放；断线实例可能保留本地旧值到本地TTL；旧 loader 也可能在删除后回填 | 提交后通知只解决部分时序；内容版本/代际、防旧回填与失联恢复需要另行闭合 |
| 事务时序 | 编辑和标签更新有数据库事务 | `updateArticle` 在提交前 evict；读者可能取到旧DB值再回填，事务提交后仍旧 | 用受控并发时序验证提交、失效、回源和回填；afterCommit不是全部一致性保证 |
| Redis故障 | 已命中的正文L1可被读取 | manager 只处理 InterruptedException；Bloom/L2/锁错误无明确隔离。详情后段仍访问Redis，不能声称L1保证整接口脱离Redis | 区分权限失败必须拒绝、统计允许降级、正文允许旧值的边界；禁止无界全量回源 |
| 预热/热榜 | 已有加权热度分、置顶/阈值候选、后台预热与计时 | 首页仍查出匹配列表后内存分页并处理全部候选；预热调用普通get不会强刷已缓存旧值；热榜先删后逐条写可见空/半成品 | 后续按量级改DB分页、有限候选与预热去重；热榜采用独立新版本构建后原子切换并约束并发刷新 |
| 管理/观测 | L1 recordStats；浏览、预热、热度刷新已有业务指标 | clear实际只清当前进程L1；getStats只反映L1。缺少完整回源次数、锁超时、L2/依赖失败、排队与恢复时长指标 | 精确命名管理动作；先补当前切片必要指标，不搭建全新治理平台 |

配置入口：`MultiLevelCacheProperties` 与 `application.yml` 的 `cache.multilevel`。默认 L1 1000条/5分钟、空值5分钟、锁等待3秒/租期10秒；详情 L2 基础30分钟加抖动。Bloom的100万预计元素、1%误判率只是集合配置，不是并发或吞吐能力。`RedissonConfig.useSingleServer()` 为单节点连接配置；不能宣称已经落地 Sentinel/Cluster 容灾。

## 4. 限流的两个具体问题

### 4.1 同毫秒请求合并计数

`resources/lua/rate_limit.lua:23` 使用 `ZADD key now now`，member和score都是毫秒时间。ZSet成员唯一，同一毫秒多个请求更新同一个成员；当阈值大于当前成员数时，这些请求可以继续放行，不能准确按请求数计数。Lua原子执行不会修正错误的计数单位。

应让每次请求的member唯一，时间只用作score，并明确跨实例时钟/窗口边界和Redis失败策略；也可以根据业务选择更简单的原子计数算法。本轮未执行脚本或在线复现，不将该源码结论写成线上事故。

### 4.2 资源预算和用户公平性不同

`ArticleServiceImpl:279` 的 key 是 `api:article:view:{articleId}`，默认10次/60秒，全站读同一文章共享额度。没有在 `RateLimitAspect` 中隐式附加IP或用户。修正计数后，这个阈值会使正常读者相互抢额度；它不是“每人每分钟十次”。热点资源保护与单用户防刷要明确各自key、预算和拒绝契约，阈值应依据测量。

另一个 `AccessLimitInterceptor` 使用IP+方法+URI，INCR与首次EXPIRE分两条指令，失败窗口可能留下无TTL的计数。两套实现窗口和故障语义不同。本次只审查，不把全站所有限流入口一起重构。

## 5. 队列、任务和线程池

| 现有内容 | 优点 | 仍不足的保证 |
| --- | --- | --- |
| 文章搜索同步 | 整批校验/逐ID回读当前DB状态，ES错误传播；专用AUTO ACK、3次尝试、失败副本确认后结束原消息 | 回读到写ES之间仍无内容版本栅栏；故障转存失败立即重新入队，长期故障仍需速率/恢复预算；未做真实MQ/ES联调 |
| 文章派生任务 | 有持久任务表、任务ID、结果/错误与耗时、人工重试和DLQ配置 | 任务插入后直接发MQ，调用方文章事务尚未提交；数据库提交与消息发布之间没有完整可恢复协议 |
| 任务认领 | 已有PENDING/RUNNING/SUCCESS等状态，成功重复消息可跳过 | 先select后无条件markRunning，多消费者可同时执行；RUNNING可以被人工重置；没有执行代/内容版本限制旧结果回写 |
| 消费失败 | 消费者抛AmqpRejectAndDontRequeueException，配置有全局重试与AI DLX | RETRYING状态本身不负责再次投递；实际尝试次数/死信时点需结合有效容器配置和异常分类验证，不能泛称已有自动补偿 |
| Publisher confirms | application.yml开启correlated confirms与returns；搜索故障转存显式处理确认 | AiTask普通convertAndSend未携带持久业务关联和确认后恢复流程；开关不代表每条任务投递可追溯，超时也不等于未送达 |
| 线程池 | 有界队列、命名线程、CallerRuns背压 | 每次阅读异步更新DB仍是每次写库，未降低总写量；与预热共用hotArticleExecutor，满载会把工作压回请求线程；进程崩溃没有持久重放 |
| 业务指标 | Micrometer已有浏览和预热/热榜计时 | 缺少任务最老积压年龄、消费速率、重试/故障转存量、线程池等待等；按articleId标签在内容数量增长时需注意基数 |

源码入口：`ArticleConsumer`、`ArticleSearchSyncConfig`、`RabbitMqConfig`、`AiTaskServiceImpl`、`AiArticleConsumer`、`ThreadPoolConfig`、`BlogMetrics`。`cacheRefreshPool`目前只检索到Bean声明，不能把“声明了池”算作已经实现异步刷新。

`@Transactional`只包数据库资源，不会自动把RabbitMQ、Redis和ES纳入同一事务。队列持久化、确认、消费者幂等、失败恢复分别解决不同故障；“改手动ACK”也不会自动建立它们。

## 6. 推荐演进与简历边界

1. 先做热点详情过载保护：修正限流单位/作用域，收紧锁失败后的回源，记录DB与依赖预算。先保证过载可解释，再优化命中率。
2. 继续完成缓存阶段：事务失效与旧回填、多实例与故障隔离、无效Bloom开销、导航/统计成本和热榜/预热及必要观测，明确阶段验收边界。统计聚合必须另定义丢失/去重预算，不能简单“定时写回”即完成。
3. 再完善现有队列：持久投递凭据、确认未知、原子认领、重试/执行代、旧版本回写、积压与恢复，按现有文章/搜索/派生链路验证，不调用付费模型。
4. 最后开发限量报名及取消恢复。正确基线完成后再考虑Redis Lua预筛/预扣与多实例受控负载，不复用AI任务表承载报名，不预设新平台。
