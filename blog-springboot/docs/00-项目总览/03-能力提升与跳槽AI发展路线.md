# 能力提升与跳槽 AI 发展路线

## 1. 文档目的

这份文档用于承接 `blog-springboot` 已有的就业分析、后端深度开发路线和阶段升级文档，进一步整理后续在个人能力提升、求职跳槽、AI 应用开发和深度工程化方向上的发展路线。

本文重点回答四个问题：

- 当前项目应该如何继续打磨，才能从个人项目升级为代表性作品。
- 后续哪些开发方向最能提升 Java 后端能力。
- 如果面向跳槽或求职，项目应该如何包装和表达。
- 如果想尝试 AI 甚至深度开发，应该优先补哪些工程能力。

这份文档不替代已有的详细设计文档，而是作为路线总览使用。具体设计和实施细节仍以以下文档为准：

## 2. 当前项目定位

`blog-springboot` 当前已经不适合再简单定位为博客系统。

更合适的定位是：

> 基于 Spring Boot 3 + Java 17 的内容平台与 AI 增强知识检索系统。

当前项目已经具备以下基础：

- Spring Boot 3 + Java 17 的现代后端技术栈。
- 文章、分类、标签、评论、留言、权限、日志、任务调度等基础业务。
- Caffeine + Redis 多级缓存、Redis Lua 限流、Redisson 分布式锁。
- RabbitMQ 异步消息、死信队列、Quartz 定时任务。
- Elasticsearch 搜索、Spring AI、Qdrant 向量库。
- 文章 AI 摘要、标签生成、向量化入库。
- RAG 博客问答和 SSE 写作助手。
- Actuator、Prometheus 指标、结构化日志。
- 多环境配置、Docker Compose 部署和安全配置规范。

所以后续发展重点不应该是继续新增更多边缘模块，而应该把核心链路做深。

一句话路线：

> 围绕内容平台主链路，把文章、缓存、AI、任务、测试、监控做深。

## 3. 后续总原则

### 3.1 少加散功能，多做核心链路

后续不建议优先继续新增天气、游戏、小工具、外部热榜等分散功能。

更值得投入的是：

- 文章生命周期。
- 文章热度分。
- 热点缓存预热。
- AI 任务中心。
- RAG 质量评估。
- 缓存治理体系。
- 统一任务平台。
- Testcontainers 与 CI。
- 安全配置和部署规范。

这些方向更容易体现后端岗位需要的系统设计能力。

### 3.2 从实现功能转向设计系统

当前项目已经具备功能广度，下一步要追求系统深度。

后续开发时，每一条核心链路都应该考虑：

- 当前状态是什么。
- 是否支持失败重试。
- 是否具备幂等性。
- 是否记录错误原因。
- 是否有指标和日志。
- 是否可以后台手动补偿。
- 是否有自动化测试覆盖。

这也是个人项目和工程项目之间的关键差异。

### 3.3 对外表达要收敛主线

面试或简历中不要平均介绍所有模块。

建议 80% 的表达围绕以下主线：

- 文章发布和内容管理。
- 热点文章访问性能优化。
- 多级缓存和限流。
- RabbitMQ 异步处理。
- Spring AI + Qdrant 的 RAG 能力。
- 可观测性、部署和测试。

天气、游戏、书籍、相册等模块可以作为补充，不建议作为主卖点。

## 4. 推荐实施路线

### 4.1 第一阶段：就业可信度补齐

目标：

> 让项目先成为可展示、可信、可部署的就业主项目。

建议优先完成：

- 复核仓库中是否还有真实密钥。
- 确认 `.env`、`application-private.yml`、生产密钥不进入 Git。
- 补齐 `dev / test / prod` 多环境配置说明。
- 保持 Docker Compose 部署文档可执行。
- 整理 README 中的项目定位、启动方式和核心亮点。
- 补充最小关键测试，保证核心接口可回归。

这一步不一定最酷，但对跳槽和面试非常重要。

面试中最忌讳的是项目技术栈很丰富，但配置里直接暴露真实密码、API Key、邮箱授权码或第三方 Secret。

### 4.2 第二阶段：文章热度分系统

目标：

> 把热门文章从简单浏览量排序，升级为可解释、可配置、可预热的热度模型。

建议实现：

- 新增 `ArticleHotScoreService`。
- 使用 Redis ZSet 维护热榜，例如 `blog:article:hot_score`。
- 热度分综合浏览、点赞、评论、收藏、推荐、置顶和时间衰减。
- Quartz 定时计算热度分。
- 首页热门文章从热榜读取。
- 热点文章缓存预热基于热榜驱动。
- 增加热度计算日志和 Micrometer 指标。
- 可选：新增 `article_hot_snapshot` 保存每日热度快照。

推荐热度模型：

```text
hotScore = viewCount * 1
         + likeCount * 5
         + commentCount * 8
         + favoriteCount * 10
         + recommendWeight
         + topWeight
         - timeDecay
```

能力收益：

- Redis ZSet 使用能力。
- 业务排序模型设计能力。
- 定时任务设计能力。
- 统计数据一致性处理能力。
- 推荐和缓存预热联动能力。

面试表达：

> 我没有简单按浏览量做热门文章，而是设计了文章热度分模型，综合浏览、点赞、评论、收藏、推荐权重和时间衰减，使用 Redis ZSet 维护实时热榜，并用热榜驱动首页推荐和热点缓存预热。

### 4.3 第三阶段：AI 任务中心

目标：

> 把 AI 模块从接口调用升级为可追踪、可重试、可观测的 AI 任务系统。

当前项目已经有：

- 文章摘要生成。
- 标签生成。
- 文章向量化入库。
- RAG 问答。
- SSE 写作助手。

下一步要补的是 AI 治理能力：

- AI 任务是否成功。
- 当前执行到哪一步。
- 使用了哪个模型。
- 使用了哪个 prompt 版本。
- 耗时多少。
- 错误原因是什么。
- 是否可以重试。
- 是否可以后台手动重跑。

建议新增 `ai_task` 表：

```text
ai_task
- id
- biz_type
- biz_id
- task_type
- status
- retry_count
- request_payload
- result_payload
- error_message
- model_name
- prompt_version
- started_at
- finished_at
- created_at
- updated_at
```

推荐状态：

```text
PENDING
RUNNING
SUCCESS
FAILED
RETRYING
CANCELED
```

推荐流程：

```text
文章发布
创建 AI 任务记录
发送 RabbitMQ 消息，消息体只传 taskId
消费者根据 taskId 查询任务和文章上下文
更新任务为 RUNNING
调用模型生成摘要和标签
文章切片并写入向量库
回写文章 AI 结果
更新任务为 SUCCESS
失败则记录错误并进入 RETRYING 或 FAILED
```

能力收益：

- 异步任务建模能力。
- RabbitMQ 幂等消费能力。
- 失败重试和补偿设计能力。
- AI 调用治理能力。
- 后台运营能力。

面试表达：

> 我将文章 AI 摘要、标签生成和向量入库抽象为 AI 任务中心，通过任务表记录状态、模型、prompt 版本、耗时和错误信息，配合 RabbitMQ 实现异步处理、失败重试和幂等消费，提升 AI 链路的可靠性和可观测性。

### 4.4 第四阶段：缓存治理体系

目标：

> 把当前多级缓存从工具实现升级为可治理的缓存体系。

当前已有：

- Caffeine L1。
- Redis L2。
- BloomFilter。
- Redisson 分布式锁。
- 空值缓存。
- TTL 抖动。
- Redis Lua 限流。

下一步建议补：

- `CacheKeyRegistry`：集中管理 key 模板和 TTL。
- `CacheBizType`：区分文章详情、首页、站点配置、权限、热门文章等缓存类型。
- `CacheMetrics`：统计 L1 命中、L2 命中、回源、空值缓存、锁失败。
- `CacheWarmupService`：基于文章热度分预热热点文章。
- 缓存分组失效：按文章、用户、站点配置等维度清理。
- 缓存管理接口权限校验和操作日志。

推荐枚举：

```java
public enum CacheBizType {
    ARTICLE_DETAIL,
    ARTICLE_HOME,
    SITE_CONFIG,
    HOT_ARTICLE,
    USER_PERMISSION
}
```

能力收益：

- 缓存抽象能力。
- 可观测性设计能力。
- 多实例缓存一致性理解。
- 热点 key 治理能力。
- 业务缓存和基础设施缓存的边界感。

面试表达：

> 我将分散在业务代码中的缓存逻辑抽象为统一多级缓存体系，并进一步设计缓存 key 注册、分组失效、热点预热和 Micrometer 指标，让缓存策略可配置、可观测、可治理。

### 4.5 第五阶段：RAG 质量评估

目标：

> 把 RAG 从能问答升级为可评估、可调参、可迭代。

当前 RAG 已有：

- 文章切片。
- 向量入库。
- 相似度检索。
- 上下文拼接。
- 来源返回。
- 无结果兜底。

下一步要补：

- 向量重复写入处理。
- 文章更新后的旧向量删除。
- similarity threshold。
- topK 配置化。
- prompt 模板版本。
- 召回日志。
- 评估问题集。
- 批量评估任务。

建议新增表：

```text
rag_eval_case
- id
- question
- expected_article_id
- expected_keywords
- min_score
- enabled
- created_at
```

```text
rag_eval_result
- id
- case_id
- hit
- recalled_article_ids
- answer
- score
- cost_time
- created_at
```

能力收益：

- RAG 应用工程能力。
- 向量索引生命周期管理能力。
- AI 效果评估意识。
- 参数调优能力。
- 检索和生成链路拆分能力。

面试表达：

> 我不仅实现了 RAG 问答，还设计了召回质量评估机制，通过固定问题集验证向量检索命中率，并根据评估结果调整切片大小、topK、相似度阈值和 prompt 模板。

### 4.6 第六阶段：统一任务平台

目标：

> 把系统中的维护动作统一收敛为可手动触发、可记录、可重试的任务平台。

适合纳入任务平台的动作：

- 文章热度分计算。
- 热点缓存预热。
- AI 失败任务重试。
- 历史文章向量重建。
- Elasticsearch 索引重建。
- 访问统计落库。
- 过期日志清理。

建议新增任务日志表：

```text
task_execution_log
- id
- task_code
- task_name
- trigger_type
- params
- status
- cost_time
- error_message
- started_at
- finished_at
- created_by
```

建议能力：

- 统一任务注册。
- 定时触发。
- 手动触发。
- 参数化执行。
- 执行日志。
- 成功和失败状态。
- 失败重试。
- Redisson 锁防重复执行。
- 超时控制。

面试表达：

> 我将系统中的索引重建、缓存预热、AI 重试和统计落库等维护动作统一抽象为任务平台，支持定时执行、手动触发、参数化运行、执行日志、失败重试和分布式锁保护。

### 4.7 第七阶段：Testcontainers 与 CI

目标：

> 让项目从能运行升级为可持续修改。

建议优先覆盖：

- 文章发布与更新链路。
- 缓存命中与失效。
- Redis Lua 限流。
- RabbitMQ 消费幂等。
- AI 任务状态流转。
- RAG 无结果、召回和来源去重。

建议技术手段：

- Maven Wrapper。
- GitHub Actions。
- Testcontainers。
- MySQL、Redis、RabbitMQ 容器化集成测试。
- AI 外部调用 mock。
- JaCoCo 覆盖率报告。

面试表达：

> 我为核心业务链路补充单测和集成测试，并通过 Maven Wrapper、GitHub Actions 和 Testcontainers 构建可复现的测试环境，保证文章发布、缓存、MQ 和 AI 任务链路在重构后仍然稳定。

## 6. 面向跳槽的项目包装

### 6.1 推荐项目名称

不建议写：

> 博客系统

建议写：

> 基于 Spring Boot 3 的内容平台与 AI 增强知识检索系统

### 6.2 推荐项目简介

可以写成：

> 基于 Spring Boot 3、Java 17、MyBatis-Plus、Redis、RabbitMQ、Elasticsearch、Sa-Token、Quartz 和 Spring AI 构建的内容平台后端。项目围绕文章管理、热点访问优化、异步 AI 处理、权限控制、搜索检索和 RAG 问答展开，支持文章发布后的 AI 摘要与标签生成、向量化入库以及基于站内知识的智能问答能力。

### 6.3 当前可用简历亮点

- 完成内容平台后端从传统博客架构向 Spring Boot 3 + Java 17 的升级改造。
- 实现 Caffeine + Redis 多级缓存、Redis Lua 限流和 Redisson 分布式锁，优化热点文章访问性能。
- 设计文章发布后的 RabbitMQ 异步处理链路，接入 Spring AI 完成摘要、标签抽取与向量化存储。
- 基于 Qdrant 实现站内文章 RAG 问答，支持来源返回和无结果兜底。
- 接入 Actuator、Prometheus、结构化日志和 Docker Compose，增强可观测性和部署能力。

### 6.4 完成深度开发后的简历亮点

- 设计文章热度分模型，综合浏览、点赞、评论、收藏、推荐权重和时间衰减，基于 Redis ZSet 维护热榜，并驱动首页推荐和缓存预热。
- 基于 Caffeine + Redis + Redisson 构建多级缓存体系，支持空值缓存、TTL 抖动、布隆过滤器、防击穿锁和缓存指标统计。
- 基于 RabbitMQ + AI 任务表设计文章 AI 处理中心，支持摘要生成、标签抽取、向量入库、任务状态追踪、失败重试和手动重跑。
- 基于 Spring AI + Qdrant 实现站内文章 RAG 问答，支持来源返回、无结果兜底，并通过评估问题集统计召回命中率。
- 使用 Testcontainers 和 CI 构建可复现测试环境，覆盖文章发布、缓存、MQ、AI 任务和 RAG 核心链路。

## 8. 面试讲述顺序

推荐面试时按下面顺序讲：

1. 项目定位  
   这是一个从传统博客升级而来的内容平台后端，不只是 CRUD。

2. 主业务链路  
   文章发布、分类标签、搜索、详情访问、热点统计、AI 处理、RAG 问答。

3. 性能优化  
   多级缓存、Redis Lua 限流、Redisson 锁、缓存穿透/击穿/雪崩处理。

4. 异步和 AI  
   RabbitMQ 异步处理文章 AI 摘要、标签生成、向量入库，后续通过 AI 任务中心治理。

5. 工程化  
   Spring Boot 3 升级、可观测性、Docker Compose、多环境配置、测试体系。

6. 不足和后续规划  
   AI 任务中心、RAG 质量评估、缓存治理、Testcontainers 和 CI。

这种讲法的好处是：

- 有业务主线。
- 有技术深度。
- 有工程意识。
- 能坦诚说明当前不足和下一步计划。

---

## 9. 结论

这个项目后续最值得追求的不是更多功能，而是更深链路。

推荐主线是：

```text
安全配置与部署可信度
    -> 文章热度分系统
    -> AI 任务中心
    -> 缓存治理体系
    -> RAG 质量评估
    -> 统一任务平台
    -> Testcontainers 与 CI
```

如果目标是跳槽，这条路线能把项目从“技术栈丰富”升级为“系统设计清楚、工程表达扎实”。

如果目标是 AI 应用开发，这条路线能把项目从“调用 AI 接口”升级为“具备 AI 任务治理、向量生命周期管理和 RAG 评估能力”。

如果目标是后端深度开发，这条路线能把项目从“功能型博客后端”升级为“可演进、可治理、可观测、可测试的内容平台后端工程”。

下一步最推荐先做：

> 文章热度分系统 + 基于热度分的热点缓存预热。

这条线改造范围可控，能连接文章、Redis、缓存、任务和监控，也最容易在简历和面试中讲出后端深度。
