# Backend Deep Development Roadmap

## 1. 文档目的

这份文档不是普通的优化清单，也不是 README 包装文案，而是面向 `blog-springboot` 后续深度开发的路线规划。

目标是回答三个问题：

- 这个后端项目下一步怎样继续做深，而不是继续堆功能。
- 哪些开发方向能真正提升代码质量、业务建模能力和后端工程水平。
- 后续如何把这些深度开发成果转化为就业项目中的高质量表达。

当前项目已经具备比较完整的后端基础：Spring Boot 3、Java 17、MyBatis-Plus、Redis、RabbitMQ、Elasticsearch、Sa-Token、Quartz、Spring AI、Qdrant、Redisson、Caffeine、Actuator、Prometheus、结构化日志和 Docker Compose。

下一阶段的重点不应该是继续增加更多边缘模块，而应该围绕文章、缓存、AI、任务、权限、测试这些核心链路继续做深。

一句话目标：

> 从功能型博客后端，升级为可演进、可治理、可观测、可测试的内容平台后端工程。

---

## 2. 当前项目所处阶段

项目现在已经完成了从普通博客后端到内容平台后端的第一轮升级。

已经具备的核心能力包括：

- 文章、分类、标签、评论、留言、权限、日志、任务调度等基础业务。
- Caffeine + Redis 多级缓存、Redis Lua 限流、Redisson 分布式锁。
- RabbitMQ 异步消息、文章 AI 摘要、标签生成、向量化入库。
- Spring AI + Qdrant 的 RAG 问答和 SSE 写作助手。
- Spring Boot 3 + Java 17 升级、多环境配置、Docker Compose 部署。
- Actuator、Prometheus 指标、结构化日志和初步测试。

这些能力说明项目已经有就业主项目的基础。

但是，如果希望继续提升代码水平和项目含金量，下一步不能只做表层完善，而应该进入第二阶段：

> 让核心业务链路具备状态、策略、失败处理、观测指标和测试验证。

这意味着后续开发要从“实现功能”转向“设计系统”。

---

## 3. 后续开发总原则

后续开发建议遵守以下原则。

### 3.1 少加模块，多做主线

不建议继续优先新增天气、游戏、工具类页面或孤立小模块。

更值得投入的是：

- 文章发布链路。
- 热点内容推荐。
- 多级缓存治理。
- AI 任务治理。
- RAG 质量评估。
- 任务调度平台。
- 权限审计。
- 测试与 CI 质量门禁。

这些方向更能体现 Java 后端岗位需要的能力。

### 3.2 少写堆叠式 Service，多拆业务能力

当前一些核心逻辑仍然集中在 `ArticleServiceImpl` 这类服务中。

后续应该逐步拆分为更清晰的业务能力服务，例如：

- `ArticlePublishService`: 文章发布流程编排。
- `ArticleStatsService`: 浏览量、点赞量、评论量等统计。
- `ArticleHotScoreService`: 热度分计算。
- `ArticleCacheService`: 文章缓存协调。
- `ArticleIndexService`: Elasticsearch 与向量索引维护。
- `AiTaskService`: AI 任务状态管理。
- `VectorIndexService`: 向量写入、删除、重建。

这样可以减少巨型 Service，让代码结构更接近真实后端工程。

### 3.3 每条主链路都要有状态、补偿和观测

后续做功能时，不要只考虑“正常能跑”，还要考虑：

- 当前执行到哪一步。
- 失败后能否重试。
- 重复执行是否幂等。
- 是否有日志和指标。
- 是否能在后台查看状态。
- 是否有测试覆盖关键分支。

这是个人项目走向工程项目的关键差异。

## 4. 方向一：文章核心业务深化

### 4.1 目标

把文章模块从传统 CRUD 升级为内容生命周期管理。

文章不只是新增、修改、删除，而应该具备完整状态流转：

```text
草稿 -> 待发布 -> 已发布 -> AI 处理中 -> 索引完成 -> 已下线 -> 已归档
```

同时要能表达失败状态：

```text
AI 处理失败
索引待重建
索引重建失败
缓存待刷新
```

### 4.2 建议开发内容

- 增加文章生命周期状态字段，区分内容状态、AI 状态、索引状态。
- 抽出 `ArticlePublishService` 负责发布流程。
- 抽出 `ArticleIndexService` 负责搜索索引和向量索引维护。
- 抽出 `ArticleStatsService` 负责浏览量、点赞量和评论统计。
- 发布文章时通过领域事件或应用事件驱动后续操作。
- 文章更新后触发缓存失效、搜索索引更新、向量索引重建。

推荐发布流程：

```text
校验文章参数
保存文章基础信息
保存分类和标签
提交发布事件
发送 AI 处理任务
清理文章相关缓存
更新搜索索引状态
返回发布结果
```

### 4.3 技术收益

这条线可以提升：

- 业务建模能力。
- 状态流转设计能力。
- 事务边界理解。
- 异步最终一致性理解。
- Service 职责拆分能力。

### 4.4 面试表达

可以这样讲：

> 我将原来的文章 CRUD 流程升级为内容生命周期管理，引入文章状态、AI 处理状态和索引状态，将发布、统计、缓存、搜索索引和向量索引拆分为独立服务，通过事件驱动异步处理，降低主流程耦合。

## 5. 方向二：文章热度分系统

### 5.1 目标

把热门文章从简单浏览量排序，升级为可配置的热度分模型。

热度分可以综合：

- 浏览量。
- 点赞量。
- 评论量。
- 收藏量。
- 发布时间。
- 是否置顶。
- 是否推荐。
- 时间衰减。

示例模型：

```text
hotScore = viewCount * 1
         + likeCount * 5
         + commentCount * 8
         + favoriteCount * 10
         + recommendWeight
         + topWeight
         - timeDecay
```

### 5.2 建议开发内容

- 新增 `ArticleHotScoreService`。
- 使用 Redis ZSet 存储文章热度榜。
- 定时任务周期性计算热度分。
- 文章浏览、点赞、评论后更新统计数据。
- 首页推荐和热点缓存预热基于热度分驱动。
- 增加热度分计算日志和指标。
- 可选：持久化每日热度快照，用于趋势分析。

### 5.3 推荐数据结构

Redis:

```text
blog:article:hot_score
```

MySQL 可选表：

```text
article_hot_snapshot
- id
- article_id
- hot_score
- view_count
- like_count
- comment_count
- favorite_count
- snapshot_date
- created_at
```

### 5.4 技术收益

这条线可以提升：

- Redis ZSet 使用能力。
- 排序模型设计能力。
- 定时任务设计能力。
- 统计数据一致性处理能力。
- 推荐和缓存预热联动设计能力。

### 5.5 面试表达

可以这样讲：

> 我没有简单按浏览量做热门文章，而是设计了文章热度分模型，综合浏览、点赞、评论、收藏和时间衰减，使用 Redis ZSet 维护热榜，并让首页推荐和缓存预热都基于热度分驱动。

## 6. 方向三：缓存治理体系

### 6.1 目标

把当前多级缓存从工具类升级为可治理的缓存体系。

当前已有基础：

- Caffeine L1。
- Redis L2。
- BloomFilter。
- Redisson 分布式锁。
- 空值缓存。
- TTL 抖动。
- 多实例失效广播。

下一步应该补：

- 缓存 key 注册。
- 缓存分组。
- 缓存指标。
- 缓存预热。
- 批量失效。
- 回源监控。
- 锁等待失败统计。

### 6.2 建议开发内容

- 新增 `CacheKeyRegistry`，集中管理 key 模板和 TTL。
- 新增 `CacheBizType`，区分文章详情、首页、站点配置、权限等缓存类型。
- 新增 `CacheMetrics`，暴露命中、未命中、回源、锁失败等指标。
- 新增 `CacheWarmupService`，基于热度分预热热点文章。
- 新增缓存分组失效能力，例如按文章、用户、站点配置分组清理。
- 缓存管理接口增加权限校验和操作日志。

### 6.3 推荐抽象

```java
public enum CacheBizType {
    ARTICLE_DETAIL,
    ARTICLE_HOME,
    SITE_CONFIG,
    HOT_ARTICLE,
    USER_PERMISSION
}
```

每类缓存可以定义：

- key 模板。
- 默认 TTL。
- 是否启用 L1。
- 是否允许空值缓存。
- 是否使用 BloomFilter。
- 是否参与分组失效。

### 6.4 技术收益

这条线可以提升：

- 缓存抽象能力。
- 可观测性设计能力。
- 多实例缓存一致性理解。
- 热点 key 治理能力。
- 业务缓存和基础设施缓存的边界感。

### 6.5 面试表达

可以这样讲：

> 我将原来分散在业务代码中的缓存逻辑抽象为统一多级缓存体系，并进一步设计缓存 key 注册、分组失效、热点预热和 Micrometer 指标，让缓存策略可配置、可观测、可治理。

## 7. 方向四：AI 任务中心

### 7.1 目标

把 AI 模块从“接口调用”升级为“可追踪、可重试、可观测”的 AI 任务系统。

当前 AI 链路已经能完成：

- 文章摘要生成。
- 标签生成。
- 文章切片。
- 向量入库。
- RAG 问答。
- SSE 写作助手。

下一步要解决：

- AI 任务是否成功。
- 失败后如何重试。
- 重复消费是否幂等。
- 使用了哪个模型。
- 使用了哪个 prompt。
- 耗时多少。
- 错误原因是什么。
- 是否可以后台手动重跑。

### 7.2 建议新增表

```text
ai_task
- id
- biz_type
- biz_id
- task_type
- status
- retry_count
- request_payload
- result_payload
- error_message
- model_name
- prompt_version
- started_at
- finished_at
- created_at
- updated_at
```

推荐状态：

```text
PENDING
RUNNING
SUCCESS
FAILED
RETRYING
CANCELED
```

### 7.3 推荐流程

```text
文章发布
创建 AI 任务记录
发送 MQ 任务消息
消费者读取任务 ID
加载任务和文章内容
更新任务为 RUNNING
调用模型生成摘要和标签
文章切片并写入向量库
回写文章 AI 结果
更新任务为 SUCCESS
失败则记录错误并进入重试或 FAILED
```

### 7.4 建议开发内容

- 新增 `AiTask` 实体、Mapper、Service。
- MQ 消息从传文章内容改为传任务 ID。
- AI 消费者基于任务 ID 查询上下文。
- 支持任务状态流转。
- 支持失败重试和最大重试次数。
- 支持后台查询 AI 任务列表。
- 支持手动重试失败任务。
- 记录模型名称、prompt 版本、耗时和错误信息。
- 接入 Micrometer 统计 AI 成功率、失败率、耗时。

### 7.5 技术收益

这条线可以提升：

- 异步任务建模能力。
- MQ 幂等消费能力。
- 失败重试和补偿设计能力。
- AI 调用治理能力。
- 后台运营能力。

### 7.6 面试表达

可以这样讲：

> 我将文章 AI 摘要、标签生成和向量入库抽象为 AI 任务中心，通过任务表记录状态、模型、prompt、耗时和错误信息，配合 RabbitMQ 实现异步处理、失败重试和后台手动重跑，提升 AI 链路的可靠性和可观测性。

## 8. 方向五：RAG 质量评估

### 8.1 目标

把 RAG 从“能问答”升级为“可评估、可调参、可迭代”。

当前 RAG 已有：

- 文章切片。
- 向量入库。
- 相似度检索。
- 上下文拼接。
- 来源返回。
- 无结果兜底。

下一步要补：

- 向量重复写入处理。
- 文章更新后的旧向量删除。
- similarity threshold。
- topK 配置化。
- prompt 模板版本。
- 召回日志。
- 评估问题集。
- 批量评估任务。

### 8.2 建议新增表

```text
rag_eval_case
- id
- question
- expected_article_id
- expected_keywords
- min_score
- enabled
- created_at
```

```text
rag_eval_result
- id
- case_id
- hit
- recalled_article_ids
- answer
- score
- cost_time
- created_at
```

### 8.3 建议开发内容

- 抽出 `RagQueryService`，专门处理 RAG 检索和上下文构造。
- 抽出 `VectorIndexService`，统一处理向量新增、删除、重建。
- 增加文章更新后的旧向量清理机制。
- 增加 RAG 评估用例管理。
- 增加批量评估任务，统计召回命中率。
- 将切片大小、overlap、topK、threshold 配置化。
- 记录每次 RAG 查询召回了哪些文章和分数。

### 8.4 技术收益

这条线可以提升：

- RAG 应用工程能力。
- 向量索引生命周期管理能力。
- AI 效果评估意识。
- 参数调优能力。
- 检索和生成链路拆分能力。

### 8.5 面试表达

可以这样讲：

> 我不仅实现了 RAG 问答，还设计了召回质量评估机制，通过固定问题集验证向量检索命中率，并根据评估结果调整切片大小、topK、相似度阈值和 prompt 模板。

## 9. 方向六：任务调度平台升级

### 9.1 目标

把 Quartz 和当前任务能力升级为统一任务平台。

后端系统中有很多维护动作：

- 文章热度分计算。
- 热点缓存预热。
- AI 失败任务重试。
- 历史文章向量重建。
- Elasticsearch 索引重建。
- 访问统计落库。
- 过期日志清理。

这些动作不应该散落在各个 Service 中，而应该由统一任务体系管理。

### 9.2 建议开发内容

- 统一任务注册。
- 支持手动触发任务。
- 支持参数化执行。
- 记录执行日志。
- 记录执行耗时。
- 记录成功和失败状态。
- 失败任务支持重试。
- 使用 Redisson 锁防止重复执行。
- 支持任务超时控制。

### 9.3 推荐任务日志表

```text
task_execution_log
- id
- task_code
- task_name
- trigger_type
- params
- status
- cost_time
- error_message
- started_at
- finished_at
- created_by
```

### 9.4 技术收益

这条线可以提升：

- 后台任务建模能力。
- Quartz 使用深度。
- 任务执行可靠性设计。
- 分布式锁使用场景理解。
- 运维后台设计能力。

### 9.5 面试表达

可以这样讲：

> 我将系统中的索引重建、缓存预热、AI 重试和统计落库等维护动作统一抽象为任务平台，支持定时执行、手动触发、参数化运行、执行日志、失败重试和分布式锁保护。

- 用户禁用。
- 文件删除。
- 配置修改。

### 10.2 建议开发内容

- 任务执行、缓存清理、AI 重试写入操作日志。
- 管理员操作增加操作者、IP、请求参数、影响对象。
- 可选：敏感操作二次确认。

### 10.3 技术收益

- 权限边界设计能力。

- 管理端治理能力。

### 10.4 面试表达

可以这样讲：

### 11.3 技术收益

## 12. 推荐实施顺序

建议不要所有方向一起做，而是按收益和依赖顺序推进。

### Phase A：文章热度分系统

周期：2 到 3 周。

目标：

- 设计文章热度分模型。
- 使用 Redis ZSet 维护热榜。
- 基于热度分驱动首页推荐和缓存预热。

## 15. 结论

这个项目后续最值得追求的不是“更多功能”，而是“更深链路”。

真正能提升代码水平和就业竞争力的，是让核心能力具备：

- 清晰的业务边界。
- 可维护的服务拆分。
- 可追踪的状态流转。
- 可补偿的失败处理。
- 可观测的指标体系。
- 可复现的测试环境。
- 可讲清楚的技术取舍。

推荐第一步从“文章热度分系统 + 基于热度的缓存预热”开始。

这条线改造范围可控，能连接文章、Redis、缓存、任务和监控，也最容易在面试中讲出深度。
